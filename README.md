# tuzi-skills

Claude Code 스킬 묶음. **소프트웨어 라이프사이클 순서**로 명령을 나눴다 —
지금 어느 단계인지만 알면 무엇을 부를지 정해진다.

규칙은 **세션 전사에서 반복된 지시를 세어** 만들었다. 같은 지시를 여러 세션에서
반복해 입력했다는 것은 그 지시가 기본 동작이 아니라는 뜻이다. 근거는
[docs/evidence.md](docs/evidence.md).

## 한눈에

```
  시작         진행             검증         보고          배포         인계
 ┌──────┐   ┌──────┬──────┐   ┌───────┐   ┌────────┐   ┌──────┐   ┌─────────┐
 │start │──▶│  go  │ fix  │──▶│ check │──▶│ report │──▶│ ship │──▶│ handoff │
 └──────┘   └──────┴──────┘   └───────┘   └────────┘   └──────┘   └─────────┘
                 ▲                                                     │
                 └──────────────── 다음 세션은 go 로 받는다 ◀───────────┘

  auto = go → check → report → ship(로컬 커밋) 을 끝까지 한 번에
  team = 여러 에이전트로 나눠 돌릴 때 (분석 → 편성 → 구성 → 위임)
  scan = 어느 단계에서든 지금 상태를 잰다 (읽기 전용 — 착수하지 않는다)
  up = 로컬에서 띄우고 · 살아 있는지 보고 · 띄운 것만 내린다
  bench = 유사 시스템·IT 동향과 비교 → 이슈 → 플랜 (문서로 남기고 착수하지 않는다)
  spec = 구현 전에 자료·대화를 분석해 기획·설계서 (요구마다 출처 · 문서만 쓰고 착수하지 않는다)
```

| 단계 | 명령 | 이렇게 말해도 된다 | 하는 일 |
| --- | --- | --- | --- |
| 1 시작 | `/start [목표]` | 새 프로젝트 만들어줘 · 이 저장소 파악해줘 | 기준선 측정 · 게이트 하나 · 얇은 끝-끝 경로 · 에이전트 운영(단일/팀) 결정 · `CLAUDE.md`(배포 시점·민감도 포함)/`HANDOFF.md` |
| 2 진행 | `/go [할 일]` | 진행해 · 계속해 · 알아서 해 | 중단 지점 복원(같은 세션이면 직전 응답의 제안이 먼저. 남은 일과 push·머지를 함께 제안했으면 남은 일 먼저, 이어서 push·머지까지) → 한 수 착수. 물을 때는 문서 번호가 아니라 내용으로. 권고 전에 결정 이력·`CLAUDE.md` 를 읽고 정한 것·단계 밖 배포는 다시 꺼내지 않는다. 워크트리 안은 묻지 않는다. 운영 기록이 없으면 파일을 고치기 전 1회 묻는다. 끝 보고에 「직접 하실 일」 |
| 2 고치기 | `/fix [증상]` | 근본 원인 해결해줘 | 원인 한 문장 → 재현 → 같은 구멍 → 강제자 |
| 3 검증 | `/check [대상]` | 확인해봐 · 캡처 남겨줘 | 첫 줄 결론 · 실물 기동 · 증거 파일 · 고치기 전 화면도 캡처 · 확인/미확인 분리 · 1라운드 상한 |
| 4 보고 | `/report [형식]` | 보고해줘 · 워드로 만들어줘 | 3열 대조 + 이유 + 영향 파일 · DB 면 ERD 차이, 화면이면 전후 비교·설명서 · 문서 산출물(Pretendard · HTML 다이어그램 렌더 확인) · 끝에 「직접 하실 일」(무엇·어디서·값이 있는 곳, 비밀값은 옮기지 않음) |
| 5 배포 | `/ship [push\|pr\|deploy]` | 커밋해줘 · pr 올려줘 | 게이트 → 브랜치 → 경로 add → 로컬 커밋. 바깥은 말한 턴에만, 원격을 다시 본 뒤. 병합 뒤 로컬 기본 브랜치 ff |
| 6 인계 | `/handoff` | 세션 넘겨 · 인수인계 | `HANDOFF.md` — `/clear` 후 `go` 한 번으로 받는다. 임계치에서 훅이 부른다 · 사용자만 할 일은 `직접:` 으로 |
| 끝까지 | `/auto <목표>` | 끝나면 알려줘 | 2→5 를 멈추지 않고. 워크트리 밖에서만 멈춘다. 운영 기록이 없으면 단일로 |
| 팀 | `/team [plan\|setup\|run\|status\|clean]` | 프로젝트 분석해서 에이전트 구성해줘 · 워커에 맡겨 | 구조·커밋 이력 분석 → 워커 명단(`docs/team.md`) → 구성 → 위임 |
| 실행 | `/up [status\|down\|logs\|clean]` | 띄워줘 · 다시 올려줘 · 꺼졌어 · 컨테이너 정리해줘 | 앱은 호스트, 미들웨어만 서비스당 컨테이너 1개 · 세션과 떨어뜨려 띄우고 응답을 본 뒤 "띄웠다" · `.tuzi/up/` 기록 한 곳 · 기록한 PID·이 프로젝트 컨테이너만 내린다. `/run` 은 내장 스킬이 쓴다 |
| 상태 | `/scan [분석 <대상>]` | 현재 상태 확인해줘 · 진행상황 알려줘 | 문서와 실제 상태 대조 → 어긋난 곳 · 남은 일 · 다음 명령 하나. 읽기 전용 — `/status` 는 내장 명령이 쓴다 |
| 벤치마크 | `/bench [주제]` | 유사 시스템 분석해줘 · 이슈 도출하고 플랜 세워줘 | 유사 시스템·최근 IT 동향 조사(출처·확인일) → 코드 근거로 비교 → 이슈 → 플랜. `docs/analysis/` 문서 |
| 설계 | `/spec [자료·주제]` | 기획서 써줘 · 설계서 만들어줘 · 화면 설계서 | 자료·대화의 요구를 출처와 함께 뽑기 → 결정 목록 → 아이디어·검증 → 화면·데이터·API·권한·단계 계획. `docs/design/` 에 판으로, 착수하지 않는다. `/design` 은 내장 명령이 쓴다 |
| 지도 | `/tuzi` | 뭐 써야 해? | 이 표 + 지금 저장소 상태에 맞는 다음 명령 하나 |

**하나만 기억한다면** — 시작할 때 `/go`, 끝까지 맡길 때 `/auto`. 자세한 사용법은 [docs/guide.md](docs/guide.md).

명령을 외울 필요는 없다. 각 스킬의 설명에 위 "이렇게 말해도 된다" 표현이 들어 있어
`진행해` · `확인해봐` 처럼 평소대로 말해도 해당 단계가 불린다.

## 설치

### 플러그인

Claude Code 안에서:

```
/plugin marketplace add itpe-ince/tuzi-skills
/plugin install tuzi@tuzi-skills
```

로컬 체크아웃으로 시험할 때:

```bash
claude --plugin-dir /경로/tuzi-skills
```

### 명령 이름 — 접두는 생략한다

플러그인 스킬의 정식 이름은 `tuzi:go` 처럼 플러그인 이름이 앞에 붙지만, **겹치는 이름이
없으면 `/go` 만 입력해도 불린다**(2026-10-05, Claude Code 2.1.289 에서 확인).
그래서 이 문서와 스킬은 모두 짧은 이름으로 적는다.

- 다른 플러그인·스킬에 같은 이름이 있으면 그때만 `/tuzi:go` 처럼 접두를 붙인다
- 지도 스킬 이름이 `help` 가 아니라 `tuzi` 인 이유 — `/help` 는 내장 명령이 가져간다

## 자동 인계

플러그인에 훅 둘이 들어 있다.

- **Stop** — 응답이 끝날 때 컨텍스트 사용률을 재서 임계치(기본 70%)를 넘으면 응답을
  끝내지 못하게 막고 `/handoff` 를 시킨다. 세션마다 한 번. 백그라운드 작업이 완료 알림을
  기다리는 중(오케스트레이션)이면 임계치 + 15%p 까지 미룬다
- **SessionStart** — `/clear`·새 실행으로 열린 세션에서 `HANDOFF.md` 가 있으면 알린다.
  착수는 시키지 않는다 — "진행해" 하면 `go` 가 받는다

인계가 끝나면 `/clear` → `/go`. `/clear` 는 훅이 대신 칠 수 없다.

| 범위 | 어디서 | 키 |
| --- | --- | --- |
| 사용자 전체 | `/config` → tuzi | `handoff_threshold` (기본 70, 0 이면 끔) · `context_window` (기본 1000000, 0 이면 자동) |
| 프로젝트 하나 | `.claude/settings.json` 의 `"env"` | `TUZI_HANDOFF_THRESHOLD` · `TUZI_CONTEXT_WINDOW` (우선) |

## 결정 이력

사용자에게 물어 정한 것과 그 결과를 저장소 안 문서(`DECISIONS.md` 가 있으면 그것, 없으면
`docs/decisions.md`)에 남긴다. 나중에 그때 무엇을 골랐고 어떻게 됐는지 볼 수 있게 하려는 것이다.

- **답을 받을 때** — 질문 도구의 답은 PostToolUse 훅이 날짜·질문·선택 항목·권고·채택을 자동으로 적는다.
  대화 문장으로 받은 답과 권고대로 진행한 결정은 스킬이 적는다
- **일이 진행되면** — `ship` 이 커밋·PR 을, `check` 가 증거를 결과 칸에 잇고 상태를 올린다
- **상태를 볼 때** — `scan` 이 오래 대기·결과 미기재·추인 필요를 보고한다

끄려면 `/config` 의 `decision_log` 를 0 으로, 프로젝트 하나만이면 `TUZI_DECISION_LOG=0`.
형식은 [skills/go/references/decisions.md](skills/go/references/decisions.md).

## 에이전트 운영

단일로 갈지 팀으로 나눌지는 **저장소마다 한 번** 정한다. 흔적은 `CLAUDE.md` 의
`## 에이전트 운영` 절이나 `docs/team.md`.

- `start` — 분석을 마치고 묻는다. 단일과 팀(명단 초안) 두 선택지 + 권고 하나
- `go` — 흔적이 없으면 파일을 고치기 전에 같은 질문을 하고 그 턴을 끝낸다. 분석·조사만
  하는 요청은 끝까지 한 뒤 보고 끝에 묻는다
- `auto` — 묻지 않고 단일로. 기록하지 않고 끝 보고에 "미결정" 을 남긴다

팀을 고르면 그 답이 명단 확인을 겸해 `team` 의 plan → setup 으로 바로 간다.

## 문서 자리

만든 문서는 그 프로젝트의 `docs/` 아래 **요청 종류별 폴더**에 둔다.
`start` 가 `CLAUDE.md` 의 `## 문서 자리` 절에 적어 어느 명령으로 만들든 같은 자리로 간다.

| 분석 | 설계 | 구현 | 검증 | 보고 | 가이드 |
| --- | --- | --- | --- | --- | --- |
| `docs/analysis/` | `docs/design/` | `docs/implementation/` | `docs/verification/` | `docs/reports/` | `docs/guides/` |

파일은 `<YYYY-MM-DD>-<주제>.md`, 이미지가 딸리면 `<YYYY-MM-DD>-<주제>/index.md` + `shots/`.
저장소에 다른 체계가 있으면 그것을 따른다. 스크린샷 원본은 `tests/screenshots/`.

## 구조

```
.claude-plugin/        plugin.json · marketplace.json
skills/<단계>/SKILL.md  라이프사이클 명령 14개
skills/report/scripts/  check_mermaid.py — HTML 의 Mermaid 가 그려졌는지 확인
skills/team/references/ 편성 설계(design) · 구성(setup) · 위임(delegation) 상세
hooks/                 자동 인계 — 컨텍스트 임계치에서 /handoff (Stop), 새 세션에 HANDOFF.md 안내 (SessionStart)
                       결정 이력 — 질문 도구의 답을 문서에 기록 (PostToolUse)
docs/guide.md          사용 가이드 — 명령별 사용법 · 상황별 시나리오 · FAQ
docs/evidence.md       근거 — 사람이 쓴 메시지 1,362건 집계
docs/skill-failures.md 스킬이 실제로 틀린 기록 — 원인과 바꾼 것
tools/harvest.py       근거를 다시 세는 스크립트
```

## 갱신

```bash
python3 tools/harvest.py ~/.claude/projects --min-count 3
```

세션 전사에서 반복 지시를 다시 세어 마크다운으로 출력한다. 새 지시가 나오면
**어느 라이프사이클 단계에서 나왔는지** 보고 그 스킬에 붙인다. 취합 절차는
[docs/evidence.md](docs/evidence.md) 3장.

## 이 저장소의 규칙

- **스킬은 도구를 지명하지 않는다.** 도구 이름이 박힌 규칙은 그 도구가 사라지면
  거짓말이 된다. 실제로 겪었다 — 2026-10-05 에 hi-loop·code-viz·bkit 을 지웠을 때
  규칙 문서만 남아 매 턴 노출됐다
- **어디서나 쓰는 확인 스크립트는 스킬에 둔다.** 같은 코드를 매번 새로 짜지 않게 — 2회 이상
  반복된 것만. 도구를 찾지 못하면 설치하지 않고 "확인 못 함" 으로 끝나야 위 규칙과 맞는다
  (`skills/report/scripts/check_mermaid.py`)
- **프로젝트 고유 지식은 스킬이 아니다.** 게이트 스크립트 이름, 바꾸면 안 되는 키 같은
  것은 그 저장소의 `CLAUDE.md`·`HANDOFF.md` 자리다 (`start` 가 뼈대를 만든다)
- **모든 턴에 적용되는 것도 스킬이 아니다.** 응답 언어·어조는 `CLAUDE.md` 다.
  스킬은 호출돼야 읽힌다
- **1회성 지시는 스킬이 아니다.** 반복된 것만 올린다
- **명령 이름은 라이프사이클 동사다.** 규칙 내용으로 이름을 짓지 않는다 — v1 이
  그래서 무엇을 불러야 할지 떠올리기 어려웠다
- **고쳤으면 계기가 된 상황을 다시 돌린다.** 전후를 PR 에 적고 실패는
  [docs/skill-failures.md](docs/skill-failures.md) 에 남긴다
- **숫자를 바꿨으면 표본을 열어 본다.** 집계만 보고 통과시켜 두 번 틀렸다
  (주입 턴 357건, 제품 도메인 어휘 81건 — 둘 다 숫자는 그럴듯했다)
