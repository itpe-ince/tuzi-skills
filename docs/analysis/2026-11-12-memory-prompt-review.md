## 2. 반복된 지시 — 기존 스킬에 없는 것

건수는 정규식 집계 뒤 표본을 열어 오탐을 뺀 근사치다.

> *"두가지를 한꺼번에 물어보니까 복잡하니 우선 메뉴 구조부터"* (ams, 10-23)
> *"그래서 파일 포맷별 파일 편집 기능들이 잘 된다는거야 안된다는거야?"* (tuzi-oa, 10-25)

실패 모양은 셋이다.

1. 문서 안에서만 쓰는 번호(D-1, N-12, 6-D, tier 4)를 설명 없이 질문에 쓴다
2. 사용자에게 확인을 맡기면서 대상·주소·절차·기대 결과를 주지 않는다
3. 여러 결정을 한 번에 묻는다. 보고가 결론(된다/안 된다)을 앞에 두지 않는다

이 저장소의 스킬이 원인 하나를 만든다. `spec` 은 결정 목록에 문서 내부 번호를 매기고
(`skills/spec/SKILL.md:55`), 결정 이력은 `D-<YYMMDD-HHMM>` 번호를 쓴다. 그 번호가 대화의 질문으로
그대로 올라온다. 묻는 형식을 정한 곳은 어느 스킬에도 없다.

### 2.2 로컬 기동과 정리 — 약 28건, 프로젝트 5개, 메모리 4건

> *"필요한 미들웨어나 플랫폼은 하나의 컨테이너로만 올리고 나머지는 로컬 호스트에서 직접 띄워줘."* (devx-collabo, 10-13)
> *"frontend 내려갔어. 다시 올려줘."* · *"백엔드 내려간거 같은데?"* · *"로컬 백엔드 또 꺼진거 아닌가?"* · *"8888포트는 왜 또 꺼져있지?"* (ams)
> *"오르카에서 에이전트가 띄운 서버 로그를 어떻게 보지?"* · *"니가 띄운 shell을 모아 볼 수 있는 방법이 뭐가 있어?"* (devx-collabo, 11-08)

메모리: `kill-own-pid-only`(패턴 pkill 이 남의 dev 서버를 죽였다) · `worker-no-broad-pkill` ·
`local-dev-host-apps`(미들웨어만 서비스당 컨테이너 1개) · `video-gen-orca-worktrees`(포트 정책).

`띄워줘` 는 `check` 의 설명에 들어 있지만 `check` 는 검증 단계다. 이 요청 다수는 "띄워 두면 내가 본다"

### 3.2 새 스킬 — `up` (로컬 기동)

2.2 의 요청은 라이프사이클의 "실행" 단계에 해당하고 지금은 맡는 스킬이 없다. 반복 건수(약 28건, 5개 프로젝트)와
메모리 4건이 README 「1회성 지시는 스킬이 아니다」 기준을 넘는다.

| 항목 | 내용 |
| --- | --- |
| 이름 | `up` — `run` 은 내장 스킬이 쓴다. 이름을 정하기 전에 `/up` 이 내장 명령에 걸리는지 확인한다(`spec` 의 2026-10-20 실패와 같은 확인) |
| 부르는 말 | 띄워줘 · 로컬 띄워줘 · 서버 올려줘 · 다시 올려줘 · 꺼졌어 · 컨테이너 정리해줘 · 뭐 떠 있어 |
| 하는 일 | ① 앱은 호스트 프로세스, 미들웨어만 서비스당 컨테이너 1개(프로젝트 `CLAUDE.md` 의 지정이 우선) ② 세션이 끝나도 살아 있게 띄우고 로그를 파일로 ③ 서비스·포트·PID·로그 경로·주소를 기록 파일 한 곳에 ④ 응답을 받아 본 뒤에 "띄웠다" 라고 한다 ⑤ `status` — 기록의 PID·포트가 살아 있는지 ⑥ `down` — 기록한 PID 만 내린다. 패턴으로 넓게 죽이지 않는다. 자기가 만든 컨테이너만 지운다 |
| `check` 와의 관계 | `check` 설명에서 `띄워줘` 를 빼고, `check` 가 기동이 필요하면 `up` 을 부른다 |

`docs/` 현행화(2.6)는 새 스킬보다 `report` 에 절을 하나 더하는 쪽을 권한다. 산출물이 문서이고 형식 규칙(폰트·자리)이 `report` 에 이미 있다.
