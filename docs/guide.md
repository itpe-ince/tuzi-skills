# tuzi 스킬 사용 가이드

2026-10-06 · 이 파일이 정본입니다. 스킬을 고치는 커밋에서 함께 고칩니다.

## 1. 시작하기

tuzi 는 Claude Code 용 스킬 묶음입니다. 명령 13개를 소프트웨어 라이프사이클(시작 → 진행 → 검증 → 보고 → 배포 → 인계) 순서로 나눠서, 지금 어느 단계인지만 알면 어떤 명령을 쓸지 정해지도록 했습니다. 규칙은 836개 세션 전사에서 사람이 직접 쓴 메시지 1,362건을 세어, 여러 번 반복된 지시만 골라 만들었습니다.

### 설치 — 플러그인 (권장)

Claude Code 안에서 아래 두 줄을 실행합니다.

```
/plugin marketplace add itpe-ince/tuzi-skills
/plugin install tuzi@tuzi-skills
```

저장소를 받아 둔 상태에서 설치 없이 시험만 하려면 다음처럼 실행합니다.

```bash
claude --plugin-dir /경로/tuzi-skills
```

### 명령 이름 — 접두는 생략합니다

플러그인 스킬의 정식 이름은 `tuzi:go` 처럼 플러그인 이름이 앞에 붙지만, 겹치는 이름이 없으면 `/go` 만 입력해도 불립니다(2026-10-05, Claude Code 2.1.289 에서 확인). 그래서 이 가이드는 모두 짧은 이름으로 적습니다.

- 다른 플러그인이나 스킬에 같은 이름이 있으면 그때만 `/tuzi:go` 처럼 접두를 붙입니다.
- 지도 스킬의 이름이 `help` 가 아니라 `tuzi` 인 이유는 `/help` 를 Claude Code 내장 명령이 쓰고 있기 때문입니다.

## 2. 한눈에 보기

명령을 하나만 기억한다면 작업을 시작할 때는 `/go`, 끝까지 맡길 때는 `/auto` 입니다. 무엇을 불러야 할지 모르면 `/tuzi` 가 지금 저장소 상태를 보고 하나를 권합니다.

```
  시작          진행             검증         보고          배포         인계
 ┌──────┐   ┌──────┬──────┐   ┌───────┐   ┌────────┐   ┌──────┐   ┌─────────┐
 │start │──▶│  go  │ fix  │──▶│ check │──▶│ report │──▶│ ship │──▶│ handoff │
 └──────┘   └──────┴──────┘   └───────┘   └────────┘   └──────┘   └─────────┘
                 ▲                                                     │
                 └──────────────── 다음 세션은 go 로 받는다 ◀───────────┘

  auto = go → check → report → ship(로컬 커밋) 을 끝까지 한 번에
  team = 이 구간을 여러 워커로 나눠 돌린다: plan → setup → run → status
  scan = 어느 단계에서든 지금 상태를 잰다 (읽기 전용)
  up = 로컬에서 띄우고 · 살아 있는지 보고 · 띄운 것만 내린다
  bench = 유사 시스템·IT 동향과 비교 → 이슈 → 플랜
  spec = 구현 전에 자료·대화를 분석해 기획·설계서
```

왼쪽에서 오른쪽으로 진행하고, 인계한 뒤 다음 세션은 다시 `go` 로 받습니다. `auto` 는 2~5단계를 한 번에 돌고, `team` 은 같은 구간을 여러 워커에게 나눠 맡깁니다.

## 3. 명령별 사용법

모든 명령은 인자 없이 불러도 됩니다. 인자가 없으면 저장소 상태(`HANDOFF.md`, git 이력, 미커밋 변경)에서 할 일을 찾습니다. 표의 "이렇게 말해도 됨" 표현을 평소처럼 쓰면 해당 명령이 불립니다.

| 명령 | 언제 | 이렇게 말해도 됨 | 하는 일 | 남는 것 | 멈추는 곳 |
| --- | --- | --- | --- | --- | --- |
| `/start [목표]` | 새 프로젝트, 처음 들어온 저장소 | 새 프로젝트 만들어줘, 이 저장소 파악해줘 | 손대기 전 기준선 측정, 검사 명령을 게이트 하나로 묶기, 끝에서 끝까지 도는 최소 경로부터 세우기, 에이전트 운영(단일/팀) 결정 받기 | `CLAUDE.md`(게이트·실행·배포 시점과 민감도·에이전트 운영·문서 자리), `HANDOFF.md`, 기준선 기록 | 스택을 고를 때(권고 하나로 물음), 에이전트 운영을 정할 때(1회), 원격 저장소 생성 |
| `/go [할 일]` | 작업을 이어갈 때 | 진행해, 계속해, 알아서 해 | 중단 지점 복원(같은 세션이면 직전 응답이 제안·질문한 것이 먼저 — 남은 일과 push·PR·merge 를 함께 제안했으면 남은 일을 먼저 끝내고, 게이트가 초록이면 다시 묻지 않고 push·PR·merge 까지 이어감. 배포는 따로 물음. 인계 문서의 결정 대기 항목은 첫머리에 모아 보임 — 문서 번호가 아니라 내용으로, 서로 걸린 결정은 앞의 것부터), 다음 할 일·권고는 결정 이력과 `CLAUDE.md` 를 먼저 읽고 정한 것·지금 단계보다 앞선 배포·다른 프로젝트의 조건을 올리지 않음, 에이전트 운영 기록 확인(없으면 파일을 고치기 전에 단일/팀을 물음. 분석·조사만 하는 요청은 묻지 않고 끝까지 한 뒤 보고 끝에 물음), 선행 조건 확인, 다음 한 수를 골라 바로 착수 | 착수 전 세 문장, 끝난 뒤 보고 | 운영 기록이 없을 때(저장소당 1회), 직전 응답이 권고하지 않은 워크트리 밖 작업·배포, 결과가 실질적으로 갈리는 선택 |
| `/fix [증상]` | 버그·실패·예상과 다른 동작 | 근본 원인 해결해줘, 또 같은 문제야 | 원인을 한 문장으로 적기, 재현, 같은 패턴을 쓰는 다른 곳 세기, 강제 수단 확인 | 원인 · 같은 패턴 · 강제자 세 줄 | 재현이 불가능할 때(근거와 함께 보고) |
| `/check [대상]` | "됐다"고 말하기 직전 | 확인해봐, 캡처 남겨줘 | 변경 성격에 맞는 실물 확인(띄우는 것은 `up` 절차로, 끝나도 내리지 않음), 증거 파일 저장, 기존 화면은 고치기 전에도 캡처, 검증은 1라운드 | 첫 줄에 결론(된다 / 안 된다 / 일부), 확인한 것 / 확인하지 않은 것 두 칸, `tests/screenshots/`, 결과서를 요청하면 `docs/verification/` | 보안·데이터 손실만 차단, 나머지는 기록 |
| `/report [형식]` | 수정을 끝내고 알릴 때, 문서 파일이 필요할 때 | 보고해줘, 대조표, 워드로 만들어줘 | 파일 · 기존 동작 · 변경 후 동작 대조표, 이유와 영향 파일. DB 가 바뀌면 ERD 차이, 화면이 바뀌면 전후 비교, 새 화면이면 설명서를 붙여 문서 파일로 만듭니다. 사용자만 할 수 있는 일(콘솔 설정·비밀값 등록·서버 작업)은 끝의 「직접 하실 일」 표에 무엇·어디서·값이 있는 곳으로 모으고, 긴 설정 안내는 `docs/guides/` 에 한 번 써서 링크합니다(비밀값 자체는 옮기지 않음). 문서 본문 폰트는 Pretendard, HTML 의 Mermaid 다이어그램은 렌더러를 넣고 함께 든 스크립트로 그려졌는지 확인합니다(브라우저가 없으면 미확인으로 보고) | 보고문, 또는 `docs/reports/` 의 md/docx/pdf/pptx/xlsx/html | 없음 |
| `/ship [push\|pr\|merge\|deploy]` | 커밋할 때, 내보낼 때 | 커밋해줘, pr 올려줘 | 게이트 → 브랜치 확인 → 경로를 지정해 add → 로컬 커밋. 내보내기 전에 원격을 다시 봐 이미 병합됐으면 다시 하지 않음, 병합 뒤 로컬 기본 브랜치(워크트리 작업이면 메인 체크아웃도) ff | 커밋, 인자가 있으면 push·PR·배포 주소 확인 | 인자 없으면 로컬 커밋에서 멈춤. 인자는 앞 단계를 포함함(`merge` 하나로 커밋·push·PR·머지) |
| `/handoff` | 세션을 넘길 때, 컨텍스트가 인계 임계치(기본 70%)에 닿았을 때 | 세션 넘겨, 인수인계 문서 써줘 | 미커밋을 먼저 정리하고 여섯 칸짜리 인계 문서 작성(할 일과 사용자 결정 대기를 나눠 적고, 사용자만 할 수 있는 일은 결정 대기에 `직접:` 으로), 끝나면 `/clear` → `/go` 안내. 임계치에 닿으면 훅이 자동으로 부름 | `HANDOFF.md` | 없음 (`/clear` 는 직접 입력) |
| `/auto <목표>` | 처음부터 끝까지 맡길 때 | 끝나면 알려줘, 다 해놔 | go → check → report → ship(로컬)을 목표가 끝날 때까지 반복. 에이전트 운영 기록이 없으면 묻지 않고 단일로 진행 | 단위별 커밋, 끝 보고(운영 미결정이면 "기다리는 것" 칸에 표시) | 워크트리 밖 작업, 갈리는 선택, 같은 실패 3회 |
| `/team [plan\|setup\|run\|status\|clean]` | 여러 에이전트로 나눠 일할 때 | 프로젝트 분석해서 에이전트 구성해줘, 워커에 맡겨 | 구조·커밋 이력 분석 → 워커 명단 → 구성 → 위임 → 상태 조회 | `docs/team.md`, 워커별 지시서 | 명단을 구성으로 넘기기 직전 한 번 |
| `/up [status\|down\|logs\|clean]` | 로컬에서 띄워 볼 때, 서버가 꺼졌을 때, 무엇이 떠 있는지·로그가 어디인지 알고 싶을 때, 컨테이너를 정리할 때 | 띄워줘, 다시 올려줘, 백엔드 꺼졌어, 뭐 떠 있어, 로그 어디서 봐, 컨테이너 정리해줘 | `CLAUDE.md`·기동 스크립트에 정해진 방식이 있으면 그대로, 없으면 앱은 호스트 프로세스·미들웨어만 서비스당 컨테이너 하나로 띄웁니다. 세션이 끝나도 살아 있게 띄우고, 주소를 호출해 응답을 본 뒤에 띄웠다고 합니다. "다시 올려줘" 는 기록 중 죽은 것만 다시 올립니다. 내릴 때는 기록한 PID 와 이 프로젝트의 컨테이너만 내리고, 이름 패턴으로 넓게 죽이지 않으며 볼륨은 지우지 않습니다 | `.tuzi/up/services.tsv`(서비스·포트·PID·주소·로그), `.tuzi/up/logs/` | 포트를 기록 밖 프로세스가 쥐고 있을 때(죽이지 않고 누구인지 보고), 볼륨·이미지 삭제 |
| `/scan [분석 <대상>]` | 지금 상태만 알고 싶을 때, 기존 시스템·요구사항을 분석할 때 | 현재 상태 확인해줘, 진행상황 알려줘, 남은 작업 정리해줘, 기존 시스템 분석해줘 | 인계 문서·`CLAUDE.md` 가 말하는 상태와 실제 상태(브랜치, 미커밋, 열린 PR, 작업 공간, 게이트)를 재서 대조하고, 어긋난 곳·남은 일(할 일과 결정 대기)·다음 명령 하나를 보고합니다. 파일을 고치거나 착수하지 않습니다 | 보고문, 문서를 요청하면 `docs/analysis/` | 없음 |
| `/bench [주제]` | 목표 시스템과 비슷한 제품·최근 동향과 비교해 방향을 잡을 때 | 벤치마크해줘, 유사 시스템 분석해줘, 이슈 도출하고 플랜 세워줘 | 비교 축을 정하고, 인지도 높은 유사 시스템 3~5개와 최근 IT 동향을 출처·확인일과 함께 조사합니다. 우리 쪽은 코드 근거로 구현 여부를 적고, 비교표 → 이슈(영향 × 비용 우선순위) → 끝-끝 단위 플랜까지 씁니다. 착수하지 않습니다 | `docs/analysis/<날짜>-benchmark-<주제>.md` | 프로젝트 목표 문장을 못 찾을 때, 이슈 트래커 등록 |
| `/spec [자료·주제]` | 구현에 들어가기 전에 기획서·요구 자료를 설계 문서로 세울 때 | 기획서 써줘, 설계서 만들어줘, 화면 설계서 만들어줘, 설계서 N판 진행해 | 첨부 자료와 대화에서 말한 기능을 요구 문장으로 뽑아 출처를 답니다. 자료가 말하지 않거나 서로 다른 곳은 결정 목록으로 모으고, 기능 목록은 아이디어·검증 두 시각을 거쳐 확정합니다. 화면(있는 화면은 캡처, 새 화면은 시안)·데이터·API·권한·비기능·단계 계획을 쓰고(단계마다 통과·실패를 가를 수 있는 검사 항목), 이전 판이 있으면 판을 올립니다. 구현은 하지 않습니다 | `docs/design/<날짜>-<주제>.md` | 결정 목록이 남았을 때(문서는 끝까지 쓰고 보고에서 물음) |
| `/tuzi` | 무엇을 불러야 할지 모를 때 | 뭐 써야 해? | 라이프사이클 지도와 지금 저장소 상태에 맞는 명령 하나 권고 | 없음 | 없음 |

### team 의 다섯 가지 인자

인자 없이 부르면 현재 상태를 보고 알맞은 단계부터 시작합니다. 명단(`docs/team.md`)이 없으면 `setup` 을 불러도 `plan` 부터 합니다.

| 인자 | 하는 일 |
| --- | --- |
| `plan <요건>` | 저장소 구조와 최근 커밋 200개에서 함께 바뀌는 영역을 재고, 이번 요건이 건드리는 영역에만 워커를 둡니다. 공유 파일마다 주인을 정합니다 |
| `setup` | 명단대로 작업 공간과 워커를 만들고, 구성 단계와 실행 단계의 경계와 완료 기준을 적습니다 |
| `run <할 일>` | 워커에게 위임합니다. 코디네이터는 코드를 고치지 않습니다. 새 일감은 그 워커의 기존 작업 공간에 맡기고, 일감마다 작업 공간을 새로 만들지 않습니다 |
| `status` | 목록을 조회한 뒤 워커 이름, 상태, 경과 시간을 보고합니다 |
| `clean` | 안 쓰는 작업 공간을 정리합니다. 명단에 없고 병합이 끝났으며 변경이 없는 공간만 지우고, 나머지는 보고만 합니다. 일감을 병합한 직후와 재개 후 첫 디스패치 전에는 말하지 않아도 코디네이터가 같은 정리를 합니다 |

### 자동 인계와 임계치 설정

tuzi 플러그인을 설치하면 자동 인계 훅 두 개가 함께 설치됩니다(결정 이력을 적는 훅은 별도입니다. 5장 자주 묻는 질문을 보세요).

- **컨텍스트 임계치 감지 (Stop 훅)** — Claude 가 응답을 끝낼 때마다 컨텍스트 사용률을 계산합니다. 임계치(기본 70%)를 넘으면 응답을 끝내지 못하게 막고 `/handoff` 를 수행하게 합니다. 한 세션에서 한 번만 동작합니다.
- **인계 문서 안내 (SessionStart 훅)** — `/clear` 나 새 실행으로 세션이 열릴 때 저장소에 `HANDOFF.md` 가 있으면 Claude 에게 그 사실을 알립니다. 작업을 저절로 시작하지는 않고, "진행해" 라고 하면 `go` 가 인계 문서부터 읽습니다.

백그라운드로 띄운 작업이 아직 완료 알림을 보내지 않았으면(코디네이터가 워커를 기다리는 오케스트레이션 중이면) 인계를 미룹니다. 기다리는 중에 막으면 조정이 끊기기 때문입니다. 작업이 끝난 뒤 응답이 멈출 때 다시 재서 인계를 겁니다. 다만 알림이 오지 않는 작업이 인계를 계속 막지 못하도록, 임계치보다 15%p 높은 지점(기본 85%)에 닿으면 미루지 않고 막습니다.

인계가 끝나면 **`/clear` 를 입력한 뒤 `/go`** 로 이어받습니다. `/clear` 는 훅이 대신 입력할 수 없어서 직접 입력해야 합니다. `/compact` 나 `/resume` 은 찬 컨텍스트를 요약이나 원본으로 되돌려 놓기 때문에 인계 뒤에는 쓰지 않습니다.

임계치는 두 곳에서 바꿀 수 있습니다. 프로젝트 설정이 사용자 설정보다 우선합니다.

| 범위 | 어디서 | 설정 |
| --- | --- | --- |
| 사용자 전체 | `/config` 의 tuzi 항목 | `handoff_threshold` (기본 70, 0 이면 끔), `context_window` (기본 1000000, 0 이면 자동) |
| 프로젝트 하나 | 그 저장소의 `.claude/settings.json` | `"env": { "TUZI_HANDOFF_THRESHOLD": "60", "TUZI_CONTEXT_WINDOW": "1000000" }` |

`context_window` 는 사용률을 계산할 때 나누는 값입니다. 기본값은 1000000 이라 기본 임계치 70% 에서는 700k 토큰에서 인계합니다. 200k 창 모델을 쓴다면 `200000` 으로 지정합니다. 0(자동)으로 두면 모델 지정에 `[1m]` 이 있거나 실제로 200k 토큰을 넘게 읽은 경우 1M 으로, 그 외에는 200k 로 계산합니다. 모델 지정은 세션을 시작할 때 받은 모델 식별자, `ANTHROPIC_MODEL` 환경 변수, 설정 파일(`.claude/settings.local.json`, `.claude/settings.json`, `~/.claude/settings.json`)의 `model` 순서로 봅니다. 대화형 세션의 모델 식별자에는 `[1m]` 이 붙지 않을 수 있습니다(2026-10-06 확인: `claude-opus-5-5`). 그러면 1M 창이어도 200k 의 70%(140k)에서 인계가 걸립니다. 이렇게 200k 로 추정해서 막을 때는 훅이 창 크기를 지정하라는 안내를 함께 띄웁니다. 이 문제 때문에 기본값을 자동이 아닌 1000000 으로 두었습니다(2026-10-06).

## 4. 상황별 시나리오

자주 있는 일곱 상황에서 어떤 순서로 부르는지 정리했습니다. 명령 대신 자연어로 말해도 같은 흐름으로 진행됩니다.

### 새 프로젝트를 시작한다

1. `/start 예약 요청을 받아 관리자 화면에 보여주는 웹앱` — 스택을 정하지 않았다면 권고 하나를 받아 고릅니다.
2. 끝에서 끝까지 도는 최소 경로(예: 버튼 하나 → 저장 → 목록에 표시)를 세운 뒤, 단일 에이전트로 갈지 팀으로 나눌지 묻습니다. 두 선택지와 권고 하나가 함께 나오고, 답은 `CLAUDE.md` 에 기록됩니다.
3. 나머지 기능은 `/auto` 로 맡깁니다.
4. 원격 저장소 생성과 push 는 따로 말해야 합니다: `/ship push`.

### 어제 하던 작업을 이어간다

1. `/go` (또는 "진행해") — `HANDOFF.md` 와 git 상태를 대조해 다음 한 수를 세 문장으로 말하고 바로 시작합니다. `/start` 를 거치지 않은 저장소라 에이전트 운영 기록이 없으면, 파일을 고치기 전에 단일/팀을 한 번 묻습니다. 분석·조사처럼 파일을 고치지 않는 요청이면 먼저 끝까지 하고 보고 끝에 묻습니다.
2. 끝나면 `/check` → `/ship`.
3. 하루를 마칠 때 `/handoff`.

### 세션이 길어졌다 (자동 인계)

1. 컨텍스트가 임계치(기본 70%)에 닿으면 훅이 응답 종료를 막고, Claude 가 `/handoff` 를 수행해 `HANDOFF.md` 를 갱신합니다.
2. "`/clear` 입력 후 `/go`" 안내가 나오면 `/clear` 를 직접 입력합니다. 훅이나 스킬은 `/clear` 를 대신 입력할 수 없습니다.
3. 새 세션에서 `/go` (또는 "진행해") — 인계 문서의 "지금 당장 할 일"부터 이어갑니다.

### 버그가 났다

1. `/fix 로그인 후 새로고침하면 세션이 풀린다` — 코드를 고치기 전에 원인을 한 문장으로 먼저 보여줍니다.
2. 고친 뒤에는 재현 경로를 다시 밟아 증상이 사라졌는지 확인합니다(`check`).
3. 보고에는 같은 패턴을 쓰는 곳이 몇 군데였고 그중 몇 곳을 고쳤는지가 들어갑니다.

### DB 나 화면이 바뀐 작업을 보고한다

1. `/report` — 바뀐 파일에 스키마나 화면이 있으면 상세 보고서를 `docs/reports/<날짜>-<주제>/index.md` 로 만듭니다.
2. 스키마가 바뀌었으면 ERD 차이(변경 요약표, 바뀐 테이블과 연결된 테이블만 그린 변경 전·후 ERD, 마이그레이션과 되돌리기 가능 여부)가 들어갑니다. 컬럼 삭제처럼 기존 데이터에 영향이 있으면 기존 행이 어떻게 되는지 적습니다.
3. 기존 화면이 바뀌었으면 변경 전·후 캡처와 번호 붙인 변경 지점 표가, 새 화면이면 화면 설명서(목적, 진입 경로, 권한, 입력 항목, 동작, 상태별 화면)가 들어갑니다.
4. 변경 전 캡처는 `/check` 가 고치기 전에 남겨 둔 것을 씁니다. 없으면 이전 버전을 띄워 찍고, 그래도 못 찍으면 못 찍은 이유를 적습니다.

### 끝까지 맡기고 다른 일을 한다

1. `/auto 주문 내역 CSV 내보내기 기능` (또는 "끝나면 알려줘")
2. 중간에 묻지 않고 구현 → 검증 → 보고 → 로컬 커밋을 반복합니다.
3. 끝 보고는 "끝났습니다" 또는 "멈췄습니다 — 어디서, 왜" 중 하나로 옵니다. push 처럼 워크트리 밖 작업은 "기다리는 것" 칸에 모입니다.

### 에이전트 팀으로 나눠 돌린다

1. `/team plan 에이전트 엔진이 실제 Task 를 DB 에 기록하도록 끝-끝 경로를 잇는다` — 저장소를 분석해 `docs/team.md` 에 명단을 쓰고, 구성으로 넘어갈지 한 번 묻습니다.
2. 승인하면 `setup` 으로 작업 공간과 워커를 만듭니다.
3. `/team run <할 일>` 로 위임하고, `/team status` 로 진행 상황을 봅니다.

실제 예시: devx-collabo 복제본에서 1번을 실행했을 때, 7개 패키지 중 요건과 관련 있는 영역만 골라 구현 워커 3개(`w-contract`, `w-engine`, `w-web`)와 검증 워커 1개(`w-check`)를 편성했습니다. sandbox, realtime, llm 등은 이유를 적고 뺐습니다.

## 5. 공통 규칙과 자주 묻는 질문

모든 명령은 아래 네 가지를 같이 지킵니다.

- **되묻지 않습니다.** 워크트리 안의 일은 하고 나서 보고합니다.
- **돌려 보지 않은 것을 됐다고 적지 않습니다.** 확인한 것과 확인하지 않은 것을 나눠 적습니다.
- **없는 식별자를 만들지 않습니다.** 근거로 인용하는 번호는 저장소에 실제로 있는 것만 씁니다.
- **도구를 지명하지 않습니다.** 그 환경에 있는 도구를 찾아 쓰고, 없으면 없다고 적습니다.

### 묻는 것과 묻지 않는 것

기준은 "되돌리기 쉬운가"가 아니라 "워크트리 밖으로 번지는가"입니다. 물어야 할 때는 안의 일을 모두 끝낸 뒤 한 번에, 권고 하나와 사유 한 줄로 묻습니다.

| 묻지 않고 한다 | 먼저 묻는다 |
| --- | --- |
| 파일·디렉터리 삭제, 덮어쓰기, 이동 | 원격 push, PR, merge, 배포 |
| 도커 컨테이너·이미지·볼륨 생성 및 삭제 | 운영 DB 의 DDL·DML |
| 개발 서버·워커 프로세스 종료, 패키지 제거 | `docker system prune` 같은 머신 전역 정리, 전역 패키지 관리자 |
| 스크립트 작성·실행, 로컬 커밋, 브랜치 생성 | `~/.claude/settings.json` 같은 권한·설정 변경 |
| 내 작업 공간(워크트리) 정리 | 메일·메시지·웹훅 등 외부로 내보내기, 비밀번호·키 교체 |

### 자주 묻는 질문

**만든 문서는 어디에 저장되나요?**
프로젝트의 `docs/` 아래에 요청 종류별로 나눠 저장합니다. 분석은 `docs/analysis/`, 설계는 `docs/design/`, 구현은 `docs/implementation/`, 검증은 `docs/verification/`, 보고는 `docs/reports/`, 가이드는 `docs/guides/` 입니다. 파일 이름은 `<날짜>-<주제>.md` 이고, 이미지가 딸리면 같은 이름의 폴더에 `index.md` 와 `shots/` 를 둡니다. 저장소에 이미 다른 문서 체계가 있으면 그것을 따릅니다. `/start` 가 이 규칙을 프로젝트 `CLAUDE.md` 의 「문서 자리」 절에 적어 두기 때문에, 어느 명령으로 만든 문서든 같은 자리에 갑니다.

**단일 에이전트로 할지 팀으로 할지는 언제 정하나요?**
저장소마다 한 번 정합니다. `/start` 는 분석을 마친 뒤 묻고, `/start` 를 거치지 않은 저장소에서는 `/go` 가 파일을 고치기 전에 한 번 묻습니다(분석·조사만 하는 요청은 끝까지 한 뒤 보고 끝에 묻습니다). 두 경우 모두 분석 결과와 권고 하나를 보여 주고, 답은 `CLAUDE.md` 의 `## 에이전트 운영` 절에 기록되어 다시 묻지 않습니다. 팀을 고르면 그 답이 명단 확인을 겸해서 바로 구성으로 넘어갑니다. `/auto` 는 중간에 묻지 않으므로 기록이 없으면 단일로 진행하고, 끝 보고에 "에이전트 운영 미결정"을 남깁니다. 나중에 바꾸려면 `/team plan` 을 부르거나 "단일로 가자"라고 말하면 됩니다.

**명령을 꼭 입력해야 하나요?**
아니요. 각 스킬 설명에 "진행해", "확인해봐", "커밋해줘" 같은 표현이 들어 있어 평소처럼 말해도 불립니다. 다만 자연어 호출은 모델이 판단하는 것이라, 확실히 불러야 할 때는 명령을 쓰는 편이 안전합니다.

**"커밋해줘"라고 하면 push 도 하나요?**
하지 않습니다. 로컬 커밋에서 멈춥니다. push 는 `/ship push` 처럼 그 턴에 따로 말해야 합니다. "이번만 push 해줘"는 한 번 허가이고, "앞으로는 묻지 말고 push 해"는 정책으로 기록합니다.

**scan 과 go 는 어떻게 다른가요?**
둘 다 지금 상태를 먼저 봅니다. `go` 는 본 뒤에 다음 한 수를 골라 착수하고, `scan` 은 보고만 하고 멈춥니다. 상태만 알고 싶을 때 `go` 를 부르면 원하지 않은 작업이 시작될 수 있습니다. 이름이 `/status` 가 아닌 것은 Claude Code 내장 명령이 그 이름을 쓰기 때문입니다.

**기획서를 설계 문서로 만들려면 무엇을 부르나요?**
`/spec` 입니다. 이름이 `/design` 이 아닌 것은 Claude Code 내장 명령이 그 이름을 쓰기 때문입니다. `/go` 에 할 일을 적어도 문서는 나오지만, 요구마다 출처를 달고 빈 곳을 결정 목록으로 모으는 절차는 `spec` 에만 있습니다. 대화에서 말한 기능도 자료로 취급하므로, 첨부 자료에 없더라도 앞서 말씀하신 기능은 요구 표에 들어갑니다.

**예전에 무엇을 골랐고 어떻게 됐는지 보려면요?**
저장소의 `DECISIONS.md` 또는 `docs/decisions.md` 를 보면 됩니다. 결정마다 날짜, 질문, 선택 항목, 권고, 채택, 결정자, 이유, 결과, 상태가 있습니다. 질문 창에서 고른 답은 훅이 자동으로 적고, 커밋·PR 과 검증 결과는 `ship` 과 `check` 가 잇습니다. 결과가 비었거나 오래 대기 중인 결정은 `/scan` 이 알려 줍니다. 파일은 작업 트리에 쌓이므로 커밋해야 원격에 남습니다. 끄려면 `/config` 의 `decision_log` 를 0 으로 합니다.

**"띄워줘" 는 check 와 up 중 무엇이 받나요?**

`up` 입니다. `check` 는 변경이 실제로 동작하는지 증거를 남기는 검증이고, `up` 은 띄워 두고 사용자가 보는 실행입니다. `check` 가 화면을 봐야 하면 `up` 절차로 띄우고, 검증이 끝나도 내리지 않습니다. 띄운 것은 저장소의 `.tuzi/up/services.tsv` 한 곳에 기록되므로, 다음 세션에서 "꺼졌어" 라고만 해도 무엇을 다시 올릴지 압니다. 모든 로그는 `.tuzi/up/logs/` 에 있어서 `tail -f` 로 직접 따라 볼 수 있습니다. 이름이 `/run` 이 아닌 것은 Claude Code 내장 스킬이 그 이름을 쓰기 때문입니다.

**한 번 거절한 제안을 Claude 가 또 꺼내지 않게 하려면요?**

거절하거나 "그냥 둬" 라고 하시면 결정 이력(`docs/decisions.md`)에 "하지 않는다" 로 남습니다. `go`·`check`·`spec`·`bench`·`handoff`·`auto`·`report` 는 다음 할 일이나 권고를 적기 전에 이 기록과 `CLAUDE.md` 를 읽고, 이미 정한 것은 다시 올리지 않습니다. 배포를 언제 할지는 `CLAUDE.md` 의 `## 배포` 절에 적어 두시면 됩니다. 예를 들어 "로컬에서 전체 기능이 끝난 뒤 한 번" 이라고 적으면 그 전에는 배포나 CI 를 권하지 않고, "정식 운영 전" 이라고 적으면 배포할 때 경고나 재확인 질문을 붙이지 않습니다. 다른 프로젝트에서 본 조건(폐쇄망 같은 운영 환경)은 이 프로젝트의 제약으로 끌어오지 않고, 관련이 있어 보이면 한 번만 묻습니다. 보안 사고, 데이터 손실, 운영 장애는 예외로 단계와 관계없이 알립니다.

**제가 직접 해야 하는 일은 어디서 보나요?**

보고 끝의 「직접 하실 일」 표입니다. 외부 콘솔의 앱 등록, 저장소·CI 의 비밀값 등록, 서버에서 할 작업처럼 Claude 가 이 환경에서 할 수 없는 일만 모아 무엇을, 어디서(메뉴 경로나 주소), 어떤 값으로(키 이름과 그 값이 있는 곳) 하는지 적습니다. 없으면 "없음" 이라고 적습니다. 두세 단계를 넘는 설정 안내는 `docs/guides/` 에 한 번 쓰고 링크하므로, 나중에 "설정 방법 다시 알려줘" 라고 하면 그 문서를 가리킵니다. 대화에 비밀값을 붙여 넣으셔도 보고·문서·커밋·`HANDOFF.md` 에는 옮기지 않고, 무시 목록에 든 `.env` 같은 로컬 파일에만 씁니다. 세션을 넘기면 `HANDOFF.md` 의 「기다리는 것」 에 `직접:` 으로 남고, 다음 `/go` 가 끝났는지 확인해 안 됐으면 첫머리에 다시 보여 줍니다.

**Claude 가 묻는 질문은 어떤 모양인가요?**
결정을 물을 때는 무엇을 정하는지 한 문장, 지금 왜 묻는지, 선택지마다 무엇이 달라지는지, 권고 하나를 적습니다. 설계서의 `D-1` 같은 번호만으로 묻지 않고, 번호는 필요하면 괄호에만 둡니다. 서로 걸린 결정은 앞의 것 하나만 묻고 나머지는 "다음에 물을 것" 으로 한 줄 남깁니다. 직접 확인을 부탁할 때는 대상, 주소나 명령, 절차, 기대 결과를 함께 적습니다. 형식은 `skills/go/references/asking.md` 에 있습니다.

**auto 와 go 는 어떻게 다른가요?**
`go` 는 한 단위를 끝까지 하고 알립니다. `auto` 는 목표가 끝날 때까지 여러 단위를 구현·검증·보고·커밋으로 반복하고, 같은 실패가 3회 반복되면 멈춥니다.

**검증을 더 돌리고 싶으면요?**
기본은 1라운드입니다. 과거에 커밋 하나에 검증을 5라운드 돌리는 동안 제품이 한 번도 돌지 않았던 사례가 있어서 상한을 두었습니다. 더 필요하면 `/check` 를 다시 부르면 됩니다.

**규칙을 고치거나 늘리려면요?**
`python3 tools/harvest.py ~/.claude/projects --min-count 3` 으로 세션 전사에서 반복 지시를 다시 센 뒤, 새 지시가 나온 라이프사이클 단계의 스킬에 붙입니다. 숫자만 보지 말고 표본을 먼저 열어 봅니다. 자세한 절차는 [evidence.md](evidence.md) 3장에 있습니다.
