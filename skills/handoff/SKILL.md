# 6. 인계한다

입력: `$ARGUMENTS` (덧붙일 메모. 비어도 된다)

## 왜 이 단계가 있나

사용자가 직접 물었다 — *"최대 토큰량에서 70% 내외일 때 세션을 넘겨야 하지 않나"*.
그리고 `진행해` 가 70회 이상 반복된 이유의 절반은, 다음 세션이 어디서부터 이어야
할지 몰랐기 때문이다. **인계가 좋으면 다음 `/go` 가 되묻지 않는다.**

## 언제

- 컨텍스트가 **인계 임계치(기본 70%)** 에 닿았다 — 새 작업을 시작하지 말고 인계한다.
  플러그인의 Stop 훅이 재서 `[tuzi] 컨텍스트 N% 사용` 으로 알린다. 그 알림이 오면 하던 단위를
  새로 벌리지 말고 바로 이 절차를 밟는다
- 한 단위가 끝나 커밋했다 — 다음 할 일을 적어 둔다
- 사용자가 요청했다

## 절차

### 1. 먼저 상태를 잰다

```bash
git status --short; git log --oneline -5; git branch --show-current
```

### 2. 미커밋을 처리한다

남길 변경이면 `/ship` 으로 로컬 커밋한 **뒤에** 인계 문서를 쓴다.

> 무슨 일이 일어나나 — 인계 문서를 먼저 쓰고 커밋하면, 문서의 "미커밋 변경 둘을
> 커밋해야 한다" 가 커밋 뒤 이미 해결된 상태로 발견된다. **인계 문서는 자기 자신을
> 반영하지 못한다.** 그래도 남으면 읽는 쪽이 `git status` 로 대조한다(`/go`).

### 3. `HANDOFF.md` 를 쓴다 (저장소 루트, 있으면 덮어써서 갱신)

```markdown
# HANDOFF — <날짜> <브랜치>

## 한 줄 현황
<무엇이 되고 무엇이 안 되나>

## 지금 당장 할 일
<다음 세션의 첫 한 수. 한 문장. 선행 조건이 있으면 그것부터. 없으면 "없음 — 결정 대기">

## 기다리는 것 (사용자 결정)
- <결정할 것 — 번호 없이 읽히는 한 문장> — 권고: <하나> (<사유 한 줄>). 없으면 "없음"
  (이미 정한 것·지금 단계보다 앞선 배포는 올리지 않는다 — [제안의 범위](../go/references/proposing.md))

## 확인한 것 / 확인 안 한 것
| 무엇 | 상태 | 증거 |

## 하면 안 되는 것
- <되돌릴 수 없는 사고 목록, 바꾸면 안 되는 것>

## 자주 쓰는 명령
- 게이트: `…`
- 실행: `…`
```

여섯 칸이 전부다. 대화 경과를 옮겨 적지 않는다 — 다음 세션에 필요한 것은 경과가
아니라 **지금 할 일**이다.

**할 일과 결정을 섞지 않는다.** 머지·공개·배포처럼 사람이 정할 것을 "지금 당장 할 일"
에 적으면 다음 `/go` 는 착수할 것이 없는데도 할 일로 읽는다. 결정은 "기다리는 것" 에
두고, 결정과 무관하게 할 수 있는 일이 있으면 그것을 "지금 당장 할 일" 에 둔다.
답을 받은 결정은 여기서 지우고 [결정 이력](../go/references/decisions.md)에 남았는지 본다.
결정은 설계서 번호(`D-1`)가 아니라 내용으로 적는다 — 다음 세션의 `/go` 가 이 줄을 그대로 질문으로 옮긴다
([묻는 형식](../go/references/asking.md)).

### 4. 커밋 여부

`HANDOFF.md` 를 저장소에 남기는 관례가 있으면 `/ship` 으로 커밋한다.
관례가 없으면 만들기만 하고 보고에 "미커밋" 이라고 적는다.

## 보고

```
HANDOFF.md 갱신 — 다음 할 일: <한 문장>
`/clear` 입력 후 `/go` 로 이어받으면 됩니다.

`/compact`·`/resume` 은 쓰지 않는다 — 찬 컨텍스트가 요약이나 원본으로 되돌아온다.
`/clear` 는 훅·스킬이 대신 입력할 수 없어 사람이 친다.
```

## 임계치 바꾸기

| 범위 | 어디서 | 값 |
| --- | --- | --- |
| 사용자 전체 | `/config` 의 tuzi 항목 (플러그인 설정) | `handoff_threshold` (기본 70, 0 이면 끔) · `context_window` (기본 1000000, 0 이면 자동) |
| 프로젝트 하나 | 그 저장소 `.claude/settings.json` 의 `"env"` | `TUZI_HANDOFF_THRESHOLD` · `TUZI_CONTEXT_WINDOW` — 플러그인 설정보다 우선 |

`context_window` 는 사용률의 분모다. 기본은 1M(기본 70% → 700k 에서 인계). 200k 창 모델이면
200000 으로 박는다. 0(자동)이면 모델 지정(세션 모델 식별자 · `ANTHROPIC_MODEL` · 설정 파일의
`model`)에 `[1m]` 이 있거나 실제로 200k 토큰을 넘게 읽은 경우 1M, 아니면 200k 로 본다 — 대화형
세션의 식별자에는 `[1m]` 이 없어 1M 창이 140k 에서 막혔다. 그래서 기본이 자동이 아니다.
자동에서 200k 로 추정해 막으면 알림 끝에 그렇게 적혀 온다. 그 안내를 사용자에게 그대로 전한다.
훅은 세션마다 한 번만 막는다. 백그라운드 작업이 완료 알림을 기다리는 중(오케스트레이션)이면
임계치 + 15%p 까지 미룬다. 그 상한에서 막혔으면 알림에 그렇게 적혀 온다 — 워커·작업 상태를
조회해 `HANDOFF.md` 의 "확인한 것 / 확인 안 한 것" 에 적는다.

## 하면 안 되는 것

- 임계치를 넘겨 새 작업을 시작하는 것
- 확인 안 한 것을 "완료" 칸에 적는 것
- 대화 요약을 인계 문서로 쓰는 것
