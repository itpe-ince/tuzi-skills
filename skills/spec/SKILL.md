# 구현 전에 기획·설계를 문서로 세운다

입력: `$ARGUMENTS` (자료 경로·주제. 비었으면 이 대화에 첨부·언급한 자료와 대화에서 말한 기능)

## 왜 이 명령이 있나

설계서·기획서를 만들라는 지시가 2026-10-20 집계에서 11건 나왔다 — *"게임 만들 수 있게
기획/설계 문서로 잘 정리해줘"* · *"전체 솔루션의 화면 설계서 html로 만들어줘"* ·
*"P6 환경 프로필 기획서 써줘"* · *"응 설계서 5판 진행해"* · *"docs/analysis에 문서로 남기고
개선안 설계해줘"* · *"화면 설계서와 데이터 설계가 완료 되야 개발 진행 할 수 있다"*.

같은 집계에 이 일이 어떻게 실패하는지도 남아 있다.

| 사용자가 한 말 | 무엇이 잘못됐나 |
| --- | --- |
| *"내가 이거 있어? 저거 있어? 라고 물어볼 때마다 기획서 없다고 하잖아"* | 기획서가 사용자가 생각한 기능을 담지 못했다 |
| *"내가 아까 … 기능을 얘기했잖아. 지금까지 뭐한거야?"* | 대화에서 말한 요구가 문서에서 빠졌다 |
| *"너 혼자 기능 목록 도출하지 말고 … 아이디어 제공 에이전트와 검증 에이전트를 추가해서 검토 후에 확정"*(2회) | 한 시각으로 목록을 확정했다 |

`/go` 로도 문서는 나오지만 절차가 없어 형식과 깊이가 매번 달랐다. 그래서 따로 둔다.

**`/design` 이 아닌 이유** — Claude Code 내장 명령이 그 이름을 쓴다(Claude Design 접근 권한
관리, 2026-10-20 확인). 같은 이름이면 짧은 이름으로 불리지 않는다. `/status` → `scan` 과 같다.

## 두 규칙

1. **요구에는 출처를 단다.** 첨부 자료(파일·쪽·절), 대화(사용자가 말한 날짜·문장), 기존
   코드(경로) 중 하나. 출처 없는 기능은 "제안" 칸에 따로 둔다 — 요구와 섞으면 누가 원한 건지
   알 수 없다
2. **문서만 쓴다.** 코드·스키마·설정을 고치지 않는다. 구현은 사용자가 `/go` 로 부른다

## 절차

### 1. 자료를 모은다 — 대화도 자료다

| 자료 | 무엇을 보나 |
| --- | --- |
| 첨부·지정한 파일 | 기획서·회의록·화면 캡처·엑셀. 읽지 못한 형식이면 못 읽었다고 적는다 |
| **이 대화에서 사용자가 말한 기능** | 지나가며 말한 것까지. 빠뜨리면 위 실패가 그대로 난다 |
| 기존 문서 | `docs/` 의 이전 판 설계서·분석·로드맵. 이전 판이 있으면 새로 쓰지 않고 판을 올린다(6단계) |
| 기존 코드 | 있으면 이미 있는 화면·테이블·API — `/scan` 분석과 같은 눈으로, 위치를 근거로 |

### 2. 요구를 문장 단위로 뽑는다

| ID | 요구 (한 문장) | 출처 | 종류 | 우선 |
| --- | --- | --- | --- | --- |
| R-01 | 로그인 후 최초 워크스페이스의 대시보드가 보인다 | 대화 2026-10-14 | 화면 | 필수 |

- ID 는 이 문서 안에서만 쓰는 번호다. 자료에 이미 번호(요건 ③, M01-13 등)가 있으면 그것을 쓴다
- 종류: 화면 · 데이터 · API · 권한 · 비기능(성능·보안·운영)
- 자료가 우선순위를 말하지 않으면 비워 두고 결정 목록에 올린다 — 지어내지 않는다

### 3. 빈 곳과 충돌을 결정 목록으로 모은다

설계를 막는 것은 대개 자료가 말하지 않은 것이다. 추측으로 메우지 말고 모은다.

| 결정 필요 | 왜 막히나 | 선택지 | 권고 |
| --- | --- | --- | --- |

- 자료끼리 다른 말을 하면 충돌로 올린다(어느 쪽이 최신인지도)
- 답을 받으면 표의 행에 답과 날짜를 적고 [결정 이력](../go/references/decisions.md)에도 남긴다
- 결정이 없어도 쓸 수 있는 절은 끝까지 쓴다. 막힌 절에는 "결정 D-n 대기" 라고 적는다

### 4. 기능 목록을 혼자 확정하지 않는다

목록을 확정하기 전에 **다른 시각 둘**을 거친다.

| 역할 | 하는 일 |
| --- | --- |
| 아이디어 | 목표에 비춰 빠진 기능·더 나은 흐름을 제안한다. 제안은 "제안" 칸으로 — 요구로 섞지 않는다 |
| 검증 | 요구표와 자료를 대조해 빠진 요구·출처 없는 요구·서로 모순되는 요구를 찾는다 |

에이전트를 나눌 수 있는 환경이면 별도 에이전트로, 아니면 같은 세션에서 역할을 바꿔 한 번씩
돌린다. **결과에 두 역할이 무엇을 바꿨는지 적는다** — 적을 게 없으면 돌리지 않은 것이다.

### 5. 설계 절을 쓴다

요구표의 행이 각 절의 어디에 담겼는지 ID 로 잇는다. 어느 절에도 담기지 않은 요구가 0 이어야 한다.

| 절 | 내용 |
| --- | --- |
| 화면 | 화면 목록과 흐름(진입 → 이동). 화면마다 목적·주요 요소·상태(빈·오류·권한 없음). **이미 있는 화면은 실제 캡처로, 새 화면은 시안(HTML 등)으로** 채운다 — 사용자가 그렇게 요구했다 |
| 데이터 | 엔터티·관계(ERD)·주요 필드·기존 스키마와의 차이. 다이어그램은 텍스트(Mermaid 등)로 — HTML 이면 `/report` B 의 렌더 규칙 |
| API | 화면이 부르는 동작마다 경로·입출력·오류. 기존 API 재사용이면 위치 |
| 권한 | 역할 × 동작 표 |
| 비기능 | 성능·보안·운영에서 요구가 있거나 위험이 보이는 것만 |
| 단계 계획 | 끝-끝으로 확인할 수 있는 단위로 순서를 정하고 단계마다 **끝나면 무엇을 보나**(`check` 의 완료 기준)와 선행 조건 |

**"끝나면 무엇을 보나" 는 검사 항목으로 쓴다.** 단계마다 2~5개, 자기 판단이 아니라 바깥 증거로
통과·실패를 가를 수 있어야 한다.

| 쓰지 않는다 | 이렇게 쓴다 |
| --- | --- |
| 화면이 깔끔하다 · 품질이 좋다 · 잘 동작한다 | 390px 폭에서 가로 스크롤 0, 캡처 `shots/…` |
| 교환 요청이 동작한다 | 요청 → 수락하면 `exchanges` 행이 ACCEPTED, 채팅방 1개 생성 |

항목마다 **틀린 입력이면 실패하는지**도 적는다(권한 없는 회원의 수락 → 403). 항상 통과하는
항목은 검사가 아니다. 지금 확인 방법을 정할 수 없으면 결정 목록에 올린다.

사용자가 "화면 설계와 데이터 설계가 끝나야 개발한다" 고 했다 — 단계 계획의 첫 단계를 구현으로
잡지 않는다. 두 절이 결정 대기로 막혀 있으면 그것이 첫 단계다.

### 6. 판을 올린다 — 새 문서를 늘어놓지 않는다

이전 판이 있으면 같은 문서를 고치고 머리에 판 번호와 바뀐 점을 적는다(*"설계서 5판 진행해"*).

```markdown
> 5판 (2026-10-20) — 4판 대비: R-07·R-08 추가(대화 10-18), 워크스페이스 전환 흐름 변경(D-2 결정 반영)
```

## 산출물

- 자리: `CLAUDE.md` 의 `## 문서 자리`, 없으면 `docs/design/<YYYY-MM-DD>-<주제>.md`
  ([report B.4](../report/SKILL.md#4-어디에-두나--프로젝트-docs-를-요청-종류로-나눈다)).
  캡처·시안이 딸리면 `docs/design/<YYYY-MM-DD>-<주제>/index.md` + `shots/` · `mock/`
- 형식을 말하면(`html`·`docx`·`pptx` 등) `/report` B 의 문서 산출물 규칙(Pretendard, HTML 다이어그램 렌더)을 따른다

```markdown
# <주제> 기획·설계 (<판>판, <날짜>)

## 요약
<무엇을 누구에게 — 한 문단 · 범위 안/밖 · 결정 대기 수 · 첫 단계>

## 자료
## 요구 (R-xx · 출처)
## 제안 (출처 없음 — 아이디어 역할)
## 결정 필요 (D-xx)
## 화면
## 데이터
## API
## 권한
## 비기능
## 단계 계획
| 단계 | 담는 요구 | 끝나면 무엇을 보나(검사 항목 · 확인 방법 · 실패 조건) | 선행 조건 |
## 검토 기록 (아이디어·검증 역할이 바꾼 것)
## 확인하지 못한 것
```

## 보고

대화창에는 요약 한 문단, **결정 필요 목록(권고 하나씩)**, 요구 수와 어느 절에도 담기지 않은 요구
수(0 이어야 한다), 문서 경로를 준다. 끝에 다음 명령 하나 — 결정이 남았으면 결정을, 없으면 단계
계획 첫 단계를 `/go` 로.

## 하면 안 되는 것

- 출처 없는 기능을 요구 칸에 섞는 것
- 대화에서 사용자가 말한 기능을 자료에 없다는 이유로 빼는 것
- 자료가 말하지 않은 우선순위·수치·정책을 지어내 확정하는 것 — 결정 목록으로
- 아이디어·검증 역할을 거치지 않고 기능 목록을 확정하는 것
- 이전 판을 두고 새 날짜 문서를 하나 더 만드는 것
- 단계의 완료를 "잘 동작한다" 처럼 실패할 수 없는 말로 쓰는 것
- 설계를 쓰고 이어서 구현에 착수하는 것 — 부르는 것은 사용자다
