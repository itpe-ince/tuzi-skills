# 1. 시작한다

입력: `$ARGUMENTS` (목표 한 문장. 비었으면 현재 디렉터리를 대상으로 본다)

## 왜 이 단계가 있나

한 저장소에서 단위 테스트 1,200건이 초록인 채로 **제품이 2주간 한 번도 돌지 않았다**
(DB 의 `Task` 0건). 그 저장소가 문서에 열네 번 적은 실패 모양이 "만든 것과 쓰는 것이
끊긴 것" 이었다. 끊김은 시작할 때 생긴다 — 부품부터 쌓고 연결을 맨 끝으로 미루면
연결이 영영 오지 않는다.

그리고 **착수 전부터 빨간 검사**가 있는 저장소에서, 그게 내가 깨뜨린 것인지 원래
빨간 것인지 가르느라 시간을 썼다. 손대기 전에 재 두면 가를 일이 없다.

## 먼저 가른다 — 새 프로젝트인가, 기존 저장소인가

```bash
git rev-parse --is-inside-work-tree 2>/dev/null; ls -A | head; git log --oneline -5 2>/dev/null
```

파일이 거의 없으면 **A. 새 프로젝트**, 코드가 있으면 **B. 기존 저장소**.

## A. 새 프로젝트

### A1. 목표를 한 문장으로 적는다

`<누가> <무엇을> 하면 <무엇이> 된다`. 쓸 수 없으면 사용자에게 **그 한 문장만** 묻는다.

### A2. 스택은 지정을 따른다. 없으면 권고 하나로 묻는다

스택은 결과가 실질적으로 갈리는 선택이라 묻는 몇 안 되는 자리다. 선택지를 늘어놓지
않는다 — **권고 하나 + 이유 한 줄**로 묻고, 답에 의존하지 않는 일(디렉터리·`README`·
`.gitignore`)은 묻기 전에 해 둔다. 사용자가 이미 말했으면 묻지 않는다.

### A3. 가장 얇은 끝-끝 경로부터 세운다

기능을 넓히기 전에 **입력 → 처리 → 저장/출력** 이 한 번 이어지는 최소 경로를 먼저
돌린다. 화면이 있으면 버튼 하나, API 면 엔드포인트 하나, 잡이면 작업 한 건.

- 완료 판정: 실제로 실행해 끝에서 결과를 **눈으로 봤다** (`/check` 기준)
- 이 경로가 돌기 전에는 두 번째 기능을 시작하지 않는다

### A4. 게이트를 하나로 묶는다

`typecheck`·`lint`·`format:check`·`test` 처럼 있는 검사를 **하나의 명령**으로 `&&` 로
엮어 첫 실패에서 멈추게 한다. 이름은 스택 관례를 따른다(`check`, `verify` 등).

> 실례 — 셋만 손으로 골라 돌리고 커밋해 문서 둘이 서식 위반으로 들어갔다. lint 는
> 서식 검사기를 보지 않는다. 묶음이 있었으면 막혔다.

### A5. 첫 커밋

`/ship` 규칙을 따른다. 저장소를 새로 만든 경우 첫 커밋은 기본 브랜치에, 그 다음부터는
feature 브랜치로. **원격 저장소 생성·push 는 묻는다** (워크트리 밖이다).

## B. 기존 저장소

### B1. 읽는 순서

| 순서 | 무엇을 | 얻는 것 |
| --- | --- | --- |
| 1 | `CLAUDE.md` · `HANDOFF.md` · `README` | 고유 규칙, 지난 세션의 "지금 할 일" |
| 2 | 패키지 매니페스트의 스크립트 목록 | 게이트 이름, 실행 명령 |
| 3 | `git log --oneline -15` · 브랜치 목록 | 작업 단위의 크기와 이름 관례 |
| 4 | `docs/` 의 로드맵·설계 문서 | 다음 단계 식별자 |

### B2. 기준선을 잰다 — 손대기 전에

게이트를 **한 번** 돌려 결과를 적는다. 이미 빨간 것이 있으면 **이름과 함께** 적어
둔다. 이후 그 검사가 빨개도 "내가 깨뜨린 것이 아님" 을 가를 수 있다.

```
기준선 (손대기 전, <커밋 해시>)
- 게이트: `pnpm check` → test 3건 실패 (auth/legacy.test.ts …) — 원래 빨갛다
- 실행: `pnpm dev` 로 기동됨, / 응답 200
```

실행이 안 되면 **안 된다고 적는다.** 고치는 것은 다음 단계 일이다.

### B3. 끊긴 곳을 찾는다

만들어진 부품이 실제로 호출되는지 본다. 정의는 있는데 호출부가 없는 모듈,
테이블은 있는데 행이 0인 저장소 — 그것이 이 저장소의 진짜 다음 한 수일 수 있다.

### B4. 영역이 여럿이면 편성을 권한다

독립적으로 빌드·배포되는 영역이 둘 이상이고 할 일이 여러 영역에 걸치면, 보고의
"다음 한 수" 에 `/team plan` 을 권한다. 권하기만 한다 — 편성은 사용자가 고른다.

## 공통 — 남기는 것

### `CLAUDE.md` (없으면 만든다, 있으면 덧붙인다)

**이 저장소에만 해당하는 것만** 적는다. 일반 원칙은 이 스킬 묶음이 맡는다.

```markdown
## 게이트
`<명령>` — 커밋 전 이것 하나. 첫 실패에서 멈춘다

## 실행
`<명령>` → <주소/결과>

## 하면 안 되는 것
- <바꾸면 안 되는 키·경로·스키마>
```

### `HANDOFF.md` 뼈대

`/handoff` 형식으로 시작 상태를 적는다. 다음 세션이 `/go` 한 번으로 받는다.

## 보고

```
## 시작 상태
| 항목 | 값 |
| 목표 | … |
| 게이트 | `…` → 초록 / 빨강(무엇) |
| 실행 | `…` → 확인함 / 안 됨(왜) |
| 끝-끝 경로 | 돈다 / 아직 |

## 남긴 파일
- CLAUDE.md (신규/추가), HANDOFF.md

## 다음 한 수
- <한 문장> → `/go`
```

## 하면 안 되는 것

- 끝-끝 경로가 돌기 전에 기능을 넓히는 것
- 기준선 없이 바로 고치기 시작하는 것
- 스택 선택지를 네 개 늘어놓고 고르게 하는 것
- 일반 원칙을 `CLAUDE.md` 에 옮겨 적는 것 — 프로젝트 고유 지식만 둔다
