# 팀으로 일한다

입력: `$ARGUMENTS`

## 무엇을 읽나

| 인자 / 말 | 읽을 문서 | 핵심 한 줄 |
| --- | --- | --- |
| `plan` · 분석해서 구성 · 에이전트 군단 · 영역별로 | [references/design.md](references/design.md) | 워커 수는 디렉터리 수가 아니다. 경계·함께 바뀜·이번 요건으로 명단을 짜고 `docs/team.md` 에 쓴다 |
| `setup` · 구성해줘 · 팀 구성 | [references/setup.md](references/setup.md) | 구성 요청을 "불필요" 로 건너뛰지 않는다. 구성/실행 경계와 완료 판정을 박는다 |
| `run` · 맡겨줘 · 위임해 | [references/delegation.md](references/delegation.md) | 구성된 환경에서는 코디네이터가 코드를 고치지 않는다 |
| `status` · 위임 결과 · 어떤 워커가 | [references/delegation.md](references/delegation.md) 규칙 3 | 목록을 조회한 뒤 이름을 대고 말한다. 추측으로 "대기 중" 이라 쓰지 않는다 |
| `clean` · worktree 정리 | [references/setup.md](references/setup.md) 6절 | 안 쓰는 작업 공간을 걷어낸다. 워크트리 내부라 묻지 않는다 |

인자가 없으면 **지금 구성이 있는가**부터 본다.

```
명단(docs/team.md) 없음 ──▶ plan ──(사용자 확인 1회)──▶ setup ──▶ run
명단 있음, 구성 없음  ──▶ setup ──▶ run
구성 있음            ──▶ status ──▶ 요청에 맞춰 run
```

`setup` 만 불려도 명단이 없으면 `plan` 부터 한다. 구성할 대상이 정해져야 구성할 수 있다.

## 절대 규칙 다섯

이 다섯은 가장 세게 추궁받은 지점이다. 문서를 다 읽지 못해도 이것만은 지킨다.

1. **구성 요청을 판단으로 건너뛰지 않는다** — *"구성이 필요 없어서 안한거야?"*
   구성이 과하다고 보면 **구성한 뒤에** 한 줄로 말한다
2. **구성했으면 위임한다** — *"오케스트레이션 모드로 도는게 아니라 니가 다 하고 있잖아"* (2회).
   예외는 사용자가 지켜보는 인터랙티브 화면 작업, 한 줄 수정, 읽기·조사뿐
3. **과하게 쓰지도 않는다** — *"왜 task로 돌리는거야? 멀티쓰레드로 처리하면 되는거 아닌가?"*
   같은 처리를 여러 건에 돌리는 건 코드의 병렬 처리다. 에이전트가 아니다
4. **상태는 조회한 값만** — *"지금 돌고 있는 워커는 없어. 어떤 워커가 돌고 있다는 거지?"*
   이름을 대고, 몇 분째인지 적고, 못 받은 결과는 못 받았다고 적는다
5. **작업 공간을 섞지 않는다** — 영역별로 워크트리를 나누고, 같은 파일을 두 워커에
   맡기지 않는다. 코디네이터가 직접 고쳤으면 워커 공간으로 가는 경로를 적는다

## 도구를 추측하지 않는다

오케스트레이션 수단은 환경마다 다르다. 이 환경에 워크트리·에이전트·터미널 제어용
스킬이나 CLI 가 있으면 **먼저 로드해 읽고** 그 명령을 쓴다. 없으면 없다고 말한다.
