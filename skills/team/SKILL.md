# 팀으로 일한다

입력: `$ARGUMENTS`

## 무엇을 읽나

| 인자 / 말 | 읽을 문서 | 핵심 한 줄 |
| --- | --- | --- |
| `plan` · 분석해서 구성 · 에이전트 군단 · 영역별로 | [references/design.md](references/design.md) | 워커 수는 디렉터리 수가 아니다. 경계·함께 바뀜·이번 요건으로 명단을 짜고 `docs/team.md` 에 쓴다 |
| `setup` · 구성해줘 · 팀 구성 | [references/setup.md](references/setup.md) | 구성 요청을 "불필요" 로 건너뛰지 않는다. 구성/실행 경계와 완료 판정을 박는다 |
| `run` · 맡겨줘 · 위임해 | [references/delegation.md](references/delegation.md) | 구성된 환경에서는 코디네이터가 코드를 고치지 않는다 |
| `status` · 위임 결과 · 어떤 워커가 | [references/delegation.md](references/delegation.md) 규칙 3 | 목록을 조회한 뒤 이름을 대고 말한다. 추측으로 "대기 중" 이라 쓰지 않는다 |
| `clean` · worktree 정리 | [references/setup.md](references/setup.md) 6절 | 안 쓰는 작업 공간을 걷어낸다. 워크트리 내부라 묻지 않는다 |

인자가 없으면 **지금 구성이 있는가**부터 본다.

```
명단(docs/team.md) 없음 ──▶ plan ──(사용자 확인 1회)──▶ setup ──▶ run
명단 있음, 구성 없음  ──▶ setup ──▶ run
구성 있음            ──▶ status ──▶ 요청에 맞춰 run
```

**`run` 으로 바로 불려도 첫 디스패치 전에 `status` 를 한 번 한다** — 작업 공간 목록을
명단과 대조해, 병합이 끝난 일감 공간은 걷고 비어 있는 워커 공간에 디스패치한다
([delegation.md](references/delegation.md) 규칙 6).

`setup` 만 불려도 명단이 없으면 `plan` 부터 한다. 구성할 대상이 정해져야 구성할 수 있다.

## 운영 결정 — 단일인가 팀인가

`start` · `go` 가 이 절을 따른다. 저장소마다 **한 번** 정하고 기록한다.

### 흔적 — 이 중 하나라도 있으면 정해진 것이다

- 저장소 `CLAUDE.md` 의 `## 에이전트 운영` 절
- `docs/team.md` (명단)

흔적이 있으면 묻지 않고 그대로 따른다. 바꾸고 싶으면 사용자가 `/team plan` 이나
"단일로 가자" 로 말한다.

### 흔적이 없으면 — 분석하고 한 번 묻는다

구조(매니페스트·디렉터리·최근 커밋)를 [references/design.md](references/design.md)
2~4단계만큼 가볍게 읽고, **권고 하나 + 이유 한 줄**로 묻는다.

```
에이전트 운영을 아직 정하지 않은 저장소입니다. 분석 결과:
- 독립 영역: apps/web · services/api (api+web 함께 바뀜 31회 / 200 커밋)
권고: 단일 에이전트 — 이번 일이 api 한 영역 안이고 두 영역이 늘 같이 바뀐다
  1. 단일 에이전트로 진행 (권고)
  2. 팀 — w-api · w-web · w-check (명단 초안)
```

- **두 선택지를 항상 다 보인다.** 권고가 분명해도 단일만 묻지 않는다. 팀 쪽에는
  워커 이름과 각자 맡을 경로를 적은 명단 초안을 붙인다 — 영역이 하나뿐이어도
  "w-main + w-check" 처럼 가장 작은 팀을 적는다. 고를 수 있게 보여 주는 것이 이 질문의 일이다
- 팀을 고르면 **그 답이 명단 확인 1회를 겸한다.** `plan` 이 `docs/team.md` 를 쓰고
  다시 묻지 않고 `setup` → `run` 으로 간다
- **묻고 그 턴을 끝낸다. 파일 수정·구현은 답을 받은 뒤다** — 단일이냐 팀이냐에 따라
  누가 고칠지가 달라지므로 구현은 "답과 무관한 일" 이 아니다. 읽기·상태 복원·기준선
  측정까지만 먼저 해 둔다
- 저장소 파일을 바꾸지 않는 요청(분석·조사·상태 확인)은 묻기 전에 끝까지 하고, 질문을
  그 보고 끝에 붙인다

### 기록한다 — 답한 즉시

```markdown
## 에이전트 운영
단일 — 2026-10-05 결정. 이유: <한 줄>. 팀으로 바꾸려면 `/team plan`
```

팀이면 `팀 — 명단은 docs/team.md` 로 적는다. **사용자가 고르지 않은 값은 기록하지
않는다** (`auto` 가 묻지 않고 단일로 진행한 경우 등) — 기록은 결정의 흔적이다.

## 절대 규칙 다섯

이 다섯은 가장 세게 추궁받은 지점이다. 문서를 다 읽지 못해도 이것만은 지킨다.

1. **구성 요청을 판단으로 건너뛰지 않는다** — *"구성이 필요 없어서 안한거야?"*
   구성이 과하다고 보면 **구성한 뒤에** 한 줄로 말한다
2. **구성했으면 위임한다** — *"오케스트레이션 모드로 도는게 아니라 니가 다 하고 있잖아"* (2회).
   예외는 사용자가 지켜보는 인터랙티브 화면 작업, 한 줄 수정, 읽기·조사뿐
3. **과하게 쓰지도 않는다** — *"왜 task로 돌리는거야? 멀티쓰레드로 처리하면 되는거 아닌가?"*
   같은 처리를 여러 건에 돌리는 건 코드의 병렬 처리다. 에이전트가 아니다
4. **상태는 조회한 값만** — *"지금 돌고 있는 워커는 없어. 어떤 워커가 돌고 있다는 거지?"*
   이름을 대고, 몇 분째인지 적고, 못 받은 결과는 못 받았다고 적는다
5. **작업 공간을 섞지도, 불리지도 않는다** — 영역별로 워크트리를 나누고, 같은 파일을 두
   워커에 맡기지 않는다. 워커 하나에 작업 공간 하나 — 새 일감은 그 공간에 디스패치하고,
   일감마다 새로 만들지 않는다. 병합한 일감 공간은 그 자리에서 걷는다 —
   *16개로 불어난 실례*가 [규칙 6](references/delegation.md) 에 있다

## 도구를 추측하지 않는다

오케스트레이션 수단은 환경마다 다르다. 이 환경에 워크트리·에이전트·터미널 제어용
스킬이나 CLI 가 있으면 **먼저 로드해 읽고** 그 명령을 쓴다. 없으면 없다고 말한다.
