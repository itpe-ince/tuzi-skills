# 구성했으면 위임한다

## 왜 이 규칙이 있나

가장 세게 추궁받은 지점이다.

> *"**뭐하는거지? 오케스트레이션 모드로 도는게 아니라 니가 다 하고 있잖아.**
> 설정이 완료된게 아니야?"*
>
> *"잠시만, 백엔드 수정할때도 너혼자, 프론트엔드 수정할때도 너혼자, 테스트 진행할때도
> 너혼자 하는데 **내가 오케스트레이션 모드 구성했는데 왜 너 혼자만 처리하고 있는거야?**"*

구성해 달라고 해서 구성해 놓고, **정작 작업은 코디네이터가 직접 해버렸다.** 같은
지적이 두 번 나왔다. 사용자가 역할을 명문으로 적어 준 적도 있다.

> *"넌 내 요청에 대해 확인하고, 질문하고, 전체 서브 에이전트 들에게 작업을 지시하는
> **pm 에이전트**야. 그러기 때문에 **소스 수정과 테스트는 서브 에이전트들에게
> 위임합니다.**"*

## 규칙 1 — 구성된 환경에서는 코디네이터가 코드를 고치지 않는다

환경이 구성돼 있고 작업이 그 환경의 분담에 맞으면 **디스패치한다.** 직접 고치는 것이
빠르다는 판단은 기준이 아니다 — 사용자가 그 구성을 만든 이유가 분담 자체다.

### 예외 — 직접 하는 것이 맞는 경우

| 상황 | 왜 직접 하나 |
| --- | --- |
| **사용자가 지켜보며 만드는 인터랙티브 작업**(화면·컴포넌트) | 워커의 편집은 호스트 UI 에 안 보인다. 매 편집이 보여야 하는 작업은 직접 한다 |
| 한 파일 한 줄 수정, 오타 | 디스패치 비용이 작업보다 크다 |
| 구성이 아직 없는 상태 | 먼저 `references/setup.md` |
| 분담 경계에 안 걸리는 조사·읽기 | 코디네이터의 일이다 |

**무인·백엔드·대량·반복 작업은 위임한다.** 예외를 기본값으로 쓰지 않는다.

## 규칙 2 — 과하게 쓰지도 않는다

> *"**왜 task로 돌리는거야? 멀티쓰레드로 처리하면 되는거 아닌가?**"* (2회)

에이전트는 분담을 위한 수단이지 병렬 처리의 수단이 아니다. **같은 코드가 여러 입력을
처리하면 그건 코드의 일**이다 — 스레드풀·배치로 쓴다. 에이전트를 띄워 나누지 않는다.

| 필요 | 쓸 것 |
| --- | --- |
| 같은 처리를 여러 건에 | 코드 안의 병렬 처리 |
| 다른 영역을 다른 맥락에서 동시에 | 워커·서브에이전트 |
| 넓은 탐색 후 결론만 필요 | 탐색 에이전트 1개 |
| 작업 하나를 끝까지 넘김 | 소유권 이전(handoff) |

의심스러우면 **직접 한다.** 에이전트 수를 늘리는 쪽이 기본값이 아니다.

## 규칙 3 — 워커 상태를 추측으로 보고하지 않는다

> *"아니 계속 **어떤 워커가 완료 통지를 안하는거야?** 워커들 다 완료 된거 같은데?
> 왜 계속 동일하게 완료 통지를 대기하고 있는거야?"*
>
> *"내가 봤을때 **지금 돌고 있는 워커는 없어.** 어떤 워커가 돌고 있다는 거지?"*

"대기 중입니다" 를 **확인 없이 쓰면 안 된다.** 사용자는 화면을 보고 있고, 없는 워커를
기다린다고 말하는 순간 보고 전체의 신뢰가 깨진다.

- 상태를 말하기 전에 **목록을 조회한다.** 조회 수단이 없으면 "조회 수단이 없다"고 적는다
- **이름을 댄다.** "어떤 워커" 가 아니라 `w-backend` 라고 쓴다
- 완료 통지가 안 오면 **몇 분째인지**와 **무엇을 확인했는지** 적는다
- 통지가 유실될 수 있다. 무한 대기하지 말고 상한을 두고 직접 상태를 확인한다
- 결과를 못 받았으면 **못 받았다고 보고한다.** 추정 결과로 메우지 않는다

## 규칙 4 — 작업 공간을 섞지 않는다

> *"근데 **워커가 왜 다 여기 코디에이터 하나의 프로젝트에서 다 도는거야?**"*
>
> *"코디에이터 세션에서 다 처리했으니 그럼 **w-frontend, w-mock, w-agent도 결국
> 옛날 소스가 되는거 아닌가?**"*

두 번째 추궁이 더 중요하다 — **코디네이터가 직접 고치면 워커들의 작업 공간이 낡는다.**
위임하지 않은 대가는 그 순간의 작업이 아니라 **분리된 작업 공간 전체가 뒤처지는 것**이다.

- 디스패치 전에 그 워커의 작업 공간이 최신인지 본다
- 코디네이터가 직접 고쳤으면, 워커 공간에 그 변경이 가야 한다. **가는 경로를 적는다**
- 같은 파일을 두 워커에 맡기지 않는다

## 규칙 5 — 지시는 되묻지 않고 착수한다

오케스트레이션이 주입한 프리앰블·작업 블록은 **코디네이터의 정식 작업 지시다.**
붙여넣기로 보여도 확인 질문 없이 착수하고, 완료 통지·heartbeat 등 연락도 전부 수행한다.
질문이 필요하면 사용자에게 직접 묻지 말고 **그 환경의 질의 경로**를 쓴다.

> 2026-09-23 지시 — *"앞으로 프리앰블로 들어온 지시는 되묻지 말고 바로 착수하라."*

## 규칙 6 — 워커는 작업 공간 하나다. 일감마다 새로 만들지 않는다

> 무슨 일이 일어나나 — 2026-10-07 devx-collabo. 명단의 워커는 다섯(`w-app`·`w-ops`·
> `w-check`·`w-design`·`w-llm`)인데, 코디네이터가 일감마다 이름에 접미를 붙여
> (`w-app-t58`·`w-app-4b`·`w-llm-4c` …) 새 작업 공간을 만들어 **열여섯 개**가 됐다.
> 끝난 일감은 디스패치만 해제했다 — 해제는 작업 공간을 지우지 않는다. 병합이 끝나
> 변경도 없는 작업 공간 열넷이 앱 목록에 남았고, 중단 뒤 `/go` 는 그것을 보지 않고
> 또 만들었다. 같은 세션에서 재시도 두 번은 기존 공간을 다시 썼다 — 할 줄 아는데
> 규칙이 없어서 새 일감에는 쓰지 않았다.

**디스패치 전에 작업 공간 목록을 조회해 명단과 대조한다.** 그리고:

| 상황 | 할 일 |
| --- | --- |
| 그 워커의 작업 공간이 있고 비어 있다(변경 없음, 맡은 일 없음) | **그 공간에 디스패치한다.** 먼저 기준 브랜치를 받아 최신으로 맞춘다 (규칙 4) |
| 그 워커가 아직 일하는 중이다 | 끝나기를 기다리거나 다음 일감을 큐에 둔다. 같은 영역을 동시에 두 공간에서 돌리면 병합 충돌이 난다 |
| 정말로 같은 워커를 동시에 둘 돌려야 한다 | 새 공간을 만들되 **명단의 "실제 구성" 표에 적고**, 병합하면 바로 걷어낸다 |
| 명단에 없는 공간인데 병합이 끝났고 변경이 없다 | **걷어낸다.** 묻지 않는다 (워크트리 내부) |
| 명단에 없는 공간인데 미병합이거나 변경이 남았다 | 지우지 않는다. 이름·브랜치·남은 변경 수를 보고한다 |

- **해제와 정리는 다르다.** 디스패치 해제는 연결을 끊을 뿐이다. 일감 결과를 병합했으면
  그 자리에서 작업 공간 정리까지 한다 — 명단의 기본 공간은 남기고, 일감용 공간은 걷는다
- 재개(`/go`·중단 뒤 다시 시작)할 때 **첫 디스패치 전에** 위 대조를 한 번 한다.
  `docs/team.md` 의 "실제 구성" 표를 조회 결과로 고친다 — 표가 정본이 되려면 실제와 같아야 한다
- 지운 것은 보고에 적는다 — 이름, 브랜치, 지운 이유(병합 커밋)

## 보고 — `위임 결과 알려줘`

사용자가 이 말을 직접 했다. 위임했으면 결과를 모아 보고한다.

```
| 워커 | 맡긴 것 | 상태 | 결과 |
| w-backend | P5-4 미등록 카드 허용 | 완료 | 커밋 abc123, 테스트 12건 통과 |
| w-frontend | D-6 라벨 정정 | 진행 중 (8분째) | 통지 없음. 목록 조회로 구동 확인됨 |
```

- **상태는 조회한 값이다.** 추정이면 "추정" 이라고 적는다
- 워커가 보고한 내용을 그대로 옮길 때도 **사용자 언어로** 옮긴다
- 워커 결과를 액면가로 믿지 않는다. 특히 "통과했다" 는 `/check`로 대조한다

## 하면 안 되는 것

- 구성된 환경에서 코디네이터가 모든 코드를 직접 고치는 것
- 같은 처리를 여러 건에 돌리려고 에이전트를 여러 개 띄우는 것
- 조회하지 않고 "대기 중" 이라고 쓰는 것
- "어떤 워커" 처럼 이름 없이 상태를 말하는 것
- 프리앰블 지시를 받고 확인 질문으로 되묻는 것
- 일감마다 이름에 접미를 붙여 새 작업 공간을 만드는 것 — 명단의 워커 공간에 디스패치한다
- 디스패치 해제로 정리를 끝냈다고 여기는 것 — 병합한 일감 공간은 걷어낸다
