# 프로젝트를 분석해 편성을 설계한다

구성(`setup.md`)보다 **앞에** 오는 단계다. 누가 몇 명, 어느 경로를 맡을지를 프로젝트에서
읽어 내 명단(roster)으로 만든다. 명단이 정해져야 구성할 것이 정해진다.

## 왜 이 규칙이 있나

사용자가 같은 요구를 두 번 했다.

> - *"요건과 현재 프로젝트 구조를 파악하여 mark console, mark 등 **각각의 영역별로
>   니가 판단하여 서브 에이전트들을 구성하는 작업부터 먼저 진행해.**"*
> - *"에이전트가 **프로젝트 분석하여** 작업을 진행할 에이전트 군단 또는 오케스트레이션
>   구성하는 스킬도 있으면 좋겠는데"* (2026-10-05)

그리고 편성이 틀렸을 때의 추궁이 남아 있다.

> - *"워커가 왜 다 여기 코디에이터 하나의 프로젝트에서 다 도는거야? w-backend 는 따로 있는데?"*
> - *"왜 task로 돌리는거야? 멀티쓰레드로 처리하면 되는거 아닌가?"* (2회)

앞의 것은 **영역을 나누지 않은 편성**, 뒤의 것은 **나눌 필요가 없는 것을 나눈 편성**이다.
편성은 많을수록 좋은 것이 아니라 **프로젝트의 경계와 맞을수록** 좋다.

## 원칙 — 워커 수는 디렉터리 수가 아니다

> **워커 하나 = 서로 독립적으로 바뀌는 영역 하나 × 그 영역에 실제로 남은 일.**

- 디렉터리가 열 개여도 이번 요건이 두 영역만 건드리면 구현 워커는 둘이다
- 늘 같이 바뀌는 두 영역은 한 워커가 맡는다. 나누면 매번 서로를 기다린다
- 같은 처리를 여러 건에 돌리는 것은 워커가 아니라 코드의 병렬 처리다
- 의심스러우면 **적게** 편성한다. 나중에 쪼개는 것이 합치는 것보다 싸다

## 절차

### 1. 요건을 한 문장으로 적는다

`$ARGUMENTS` 나 대화에서 이번 편성이 처리할 일을 한 문장으로 적는다. 요건 없이
"이 프로젝트를 위한 상설 팀" 을 원하면, 요건 대신 **최근 작업 흐름**(3단계의 커밋
이력)을 기준으로 삼는다고 적는다.

### 2. 구조를 읽어 후보 영역을 뽑는다

| 무엇을 보나 | 얻는 것 |
| --- | --- |
| 워크스페이스 선언 (모노레포 패키지 목록, 하위 매니페스트) | 이미 선언된 경계 — 가장 강한 후보 |
| 최상위 디렉터리와 각 디렉터리의 매니페스트·언어 | 빌드·런타임이 다른 경계 |
| 배포 단위 (컨테이너 정의, 서비스 목록) | 따로 뜨고 따로 죽는 경계 |
| 테스트 위치와 종류 (단위·통합·e2e) | 검증을 따로 맡길 수 있는가 |
| 코드 소유 선언 파일이 있으면 그것 | 사람이 이미 그어 둔 경계 |
| `CLAUDE.md` · `docs/` 의 아키텍처 문서 | 경계의 이름과 금지 사항 |

각 후보마다 **경로 · 언어/런타임 · 게이트 명령 · 파일 수**를 적는다.

### 3. 함께 바뀌는 정도를 잰다 — 경계가 진짜인지 확인

구조상 나뉘어 있어도 늘 같이 바뀌면 한 영역이다. 커밋 이력에서 잰다.

```bash
# 최근 200 커밋에서 커밋마다 건드린 최상위 영역 조합을 센다
git -c core.quotePath=false log -200 --name-only --pretty=format:'--' \
 | awk -F/ '/^--$/{if(s!="")print s; s=""; delete seen; next}
            NF{a=$1; if(!(a in seen)){seen[a]=1; s=s (s==""?"":"+") a}}
            END{if(s!="")print s}' \
 | sort | uniq -c | sort -rn | head -20
```

- `api+web` 이 상위에 많으면 둘은 묶는다 (또는 둘 사이의 계약을 따로 소유자에게 준다)
- 단독 출현이 대부분이면 나눈다
- 패키지가 한 단계 더 깊으면(`packages/x`) `$1` 대신 `$1"/"$2` 로 센다

이력이 짧아 의미가 없으면(커밋 20개 미만) **"이력 부족 — 구조만으로 판단"** 이라고 적는다.

### 4. 이번 요건이 건드리는 영역만 남긴다

요건 문장에서 손댈 영역을 고른다. 어디를 건드릴지 모르면 `grep` 으로 요건의 핵심어가
나오는 파일을 찾아 영역별로 센다. **일이 없는 영역에는 워커를 두지 않는다.**

### 5. 역할을 정한다

| 역할 | 몇 | 맡는 일 | 원칙 |
| --- | --- | --- | --- |
| 코디네이터 | 1 (나) | 요청 확인·질문·분배·결과 취합·보고 | **코드를 고치지 않는다** (`delegation.md` 규칙 1) |
| 구현 워커 | 4단계에서 남은 영역 수 | 소유 경로 안의 구현과 단위 테스트 | 소유 경로 밖은 쓰지 않는다 |
| 검증 워커 | 0~1 | 끝-끝 확인, 화면 캡처 (`/check`) | **자기 작업 공간에서** 돈다. 구현 워커의 공간을 고쳤다 되돌리지 않는다 |
| 계약 소유자 | 0~1 (보통 구현 워커 하나가 겸함) | 영역 사이의 공유 파일 | 아래 6단계 |

검증 워커를 따로 두는 기준 — 끝-끝 확인이 여러 영역에 걸치거나 화면 캡처가 필요할 때.
한 영역 안에서 끝나면 그 구현 워커가 직접 확인한다.

**규모 상한** — 구현 워커가 **5를 넘으면** 편성을 다시 본다. 대부분 3단계에서 묶었어야
할 영역을 나눈 것이다. 그래도 필요하면 사유를 적는다.

### 6. 공유 파일의 주인을 정한다

두 워커가 같은 파일을 고치면 병합 충돌이 쏟아진다. 영역 사이에 걸친 파일을 찾아
**주인을 하나씩** 붙인다.

- 공용 타입·API 스키마·DB 마이그레이션 → 계약 소유자 하나
- 루트 매니페스트·잠금 파일·CI 설정 → 코디네이터가 모아서 처리하거나 한 워커에 고정
- 주인이 아닌 워커는 변경이 필요하면 **코디네이터에게 요청**한다

### 7. 명단을 쓴다 — `docs/team.md`

```markdown
# 편성 — <요건 한 문장> (<날짜>)

## 명단
| 이름 | 역할 | 소유 경로 | 쓰지 않는 경로 | 게이트 | 작업 공간 |
| --- | --- | --- | --- | --- | --- |
| coordinator | 분배·취합 | — | 전부 (코드 수정 안 함) | — | 현재 체크아웃 |
| w-api | 구현 | `services/api/**` | `apps/web/**` | `pnpm -F api check` | 워크트리 `w-api` |
| w-web | 구현 | `apps/web/**` | `services/api/**` | `pnpm -F web check` | 워크트리 `w-web` |
| w-check | 검증 | — (읽기·실행만) | 소스 전부 | e2e | 워크트리 `w-check` |

## 공유 파일
| 파일 | 주인 | 다른 워커는 |
| `packages/types/**` | w-api | 코디네이터에게 요청 |

## 분석 근거
- 후보 영역: … (2단계)
- 함께 바뀜: `api+web` 31회 / 200 커밋 → 계약을 w-api 에 둠 (3단계)
- 이번 요건이 건드리는 영역: … (4단계)
- 뺀 영역과 이유: `infra/` — 이번 요건과 무관

## 워커에게 줄 지시 (워커마다 한 장)
(아래 템플릿)
```

이름은 `w-<영역>` 으로 짓는다. 사용자가 이미 쓰는 이름이 있으면 그것을 따른다.

### 8. 워커 지시서를 쓴다

워커는 대화 맥락을 모른다. 워커마다 아래를 채워 명단 끝에 둔다.

```markdown
### w-api
- 너의 일: <이번 요건 중 이 영역 몫, 한두 문장>
- 소유 경로: `services/api/**` — 이 밖은 쓰지 않는다
- 공유 파일이 필요하면: 코디네이터에게 요청 (직접 고치지 않는다)
- 게이트: `pnpm -F api check` — 초록일 때만 커밋
- 커밋: 경로 명시 add, 로컬 커밋까지 (`/ship` 규칙)
- 완료 통지: `/report` 3열 표 + 확인한 것/안 한 것
- 막히면: 멈추지 말고 막힌 지점을 통지하고 나머지를 끝낸다
```

### 9. 사용자에게 한 번 확인한다

편성은 결과가 실질적으로 갈리는 선택이다. 명단 표와 분석 근거 세 줄을 보여주고
**한 질문으로** 묻는다.

- "이 편성으로 구성까지 진행할까요?" (권고)
- 사용자가 직접 구성하길 원한 적이 있으면: "구성은 직접 하실 절차서로 드릴까요?"
- 저장소 분리 방식(한 저장소 + 워크트리 / 저장소 따로)은 `setup.md` 5절의 표로 함께 고르게 한다

명단 작성(1~8단계)은 묻지 않고 끝내 둔다. 묻는 것은 **구성으로 넘어가는 문턱**뿐이다.

### 10. 구성으로 넘긴다

확인을 받으면 `setup.md` 절차로 명단 그대로 작업 공간과 워커를 만든다. 명단과 실제
구성이 어긋나면 명단을 고친다 — 명단이 정본이다.

## 하면 안 되는 것

- 디렉터리마다 워커를 하나씩 두는 것
- 이번 요건과 무관한 영역에 워커를 두는 것
- 공유 파일의 주인을 정하지 않고 두 워커에 맡기는 것
- 검증 워커가 구현 워커의 작업 공간에서 소스를 고쳤다 되돌리는 것
- 분석 근거 없이 "프론트·백엔드·테스트" 같은 일반 편성을 내놓는 것
- 명단 확인을 받기 전에 워커를 띄우는 것
