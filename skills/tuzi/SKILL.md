# tuzi — 라이프사이클 지도

## 한 장 요약

```
  시작          진행             검증         보고          배포         인계
 ┌──────┐   ┌──────┬──────┐   ┌───────┐   ┌────────┐   ┌──────┐   ┌─────────┐
 │start │──▶│  go  │ fix  │──▶│ check │──▶│ report │──▶│ ship │──▶│ handoff │
 └──────┘   └──────┴──────┘   └───────┘   └────────┘   └──────┘   └─────────┘
                 ▲                                                     │
                 └──────────────── 다음 세션은 go 로 받는다 ◀───────────┘

  auto = go → check → report → ship(로컬 커밋) 을 끝까지 한 번에
  team = 여러 에이전트로 나눠 돌릴 때 (분석 → 편성 → 구성 → 위임)
  scan = 어느 단계에서든 지금 상태를 잰다 (읽기 전용 — 착수하지 않는다)
  up = 로컬에서 띄우고 · 살아 있는지 보고 · 띄운 것만 내린다
  bench = 유사 시스템·IT 동향과 비교 → 이슈 → 플랜 (문서로 남기고 착수하지 않는다)
  spec = 구현 전에 자료·대화를 분석해 기획·설계서 (요구마다 출처 · 문서만 쓰고 착수하지 않는다)
  decide = 결정해 달라는데 무엇을 정하라는 건지 모를 때 — 풀어 쓰고 권고 하나 (착수하지 않는다)
```

## 명령표

| 단계 | 명령 | 이렇게 말해도 된다 | 하는 일 |
| --- | --- | --- | --- |
| 1 시작 | `/start [목표]` | 새 프로젝트 만들어줘 · 이 저장소 파악해줘 | 기준선 측정 · 게이트 확정 · 얇은 끝-끝 경로 · `CLAUDE.md`/`HANDOFF.md` 뼈대 |
| 2 진행 | `/go [할 일]` | 진행해 · 계속해 · 알아서 해 | 중단 지점 복원 → 한 수 착수 → 끝까지 |
| 2 고치기 | `/fix [증상]` | 근본 원인 해결해줘 · 또 같은 문제야 | 원인 한 문장 → 재현 → 같은 구멍 → 강제자 |
| 3 검증 | `/check [대상]` | 확인해봐 · 캡처 남겨줘 · e2e 돌려줘 | 실물 기동 → 증거 파일 → 확인/미확인 분리. 1라운드 |
| 4 보고 | `/report [형식]` | 보고해줘 · 대조표 · 워드로 만들어줘 | 파일·기존·변경후 3열 + 이유 + 영향 파일. 문서 산출물 |
| 5 배포 | `/ship [push\|pr\|deploy]` | 커밋해줘 · pr 올려줘 | 게이트 → 브랜치 → 경로 add → 로컬 커밋. 바깥은 확인 |
| 6 인계 | `/handoff` | 세션 넘겨 · 인수인계 문서 | 다음 세션이 `go` 한 번으로 받을 수 있게 남긴다 |
| 끝까지 | `/auto <목표>` | 끝나면 알려줘 · qa 끝나면 갭까지 | 2→3→4→5(로컬) 를 멈추지 않고 |
| 실행 | `/up [status\|down\|logs\|clean]` | 띄워줘 · 다시 올려줘 · 꺼졌어 · 뭐 떠 있어 · 컨테이너 정리해줘 | 앱은 호스트, 미들웨어만 서비스당 컨테이너 1개 → 세션과 떨어뜨려 띄우고 응답 확인 → `.tuzi/up/` 에 서비스·포트·PID·로그 기록. 내릴 때는 기록한 PID·이 프로젝트 컨테이너만 |
| 상태 | `/scan [분석 <대상>]` | 현재 상태 확인해줘 · 진행상황 알려줘 · 기존 시스템 분석해줘 | 문서가 말하는 상태와 실제(브랜치·미커밋·PR·작업 공간·게이트)를 대조 → 어긋난 곳 · 남은 일 · 다음 명령 하나. 고치지 않는다 |
| 벤치마크 | `/bench [주제]` | 유사 시스템 분석해줘 · 최근 IT 동향 · 이슈 도출하고 플랜 세워줘 | 유사 시스템 3~5개·동향 조사(출처·확인일) → 우리 쪽은 코드 근거 → 비교표 → 이슈 → 플랜. `docs/analysis/` 에 문서 |
| 설계 | `/spec [자료·주제]` | 기획서 써줘 · 설계서 만들어줘 · 화면 설계서 · 설계서 N판 진행해 | 첨부 자료·대화의 요구를 출처와 함께 뽑기 → 빈 곳·충돌은 결정 목록 → 아이디어·검증 두 시각 → 화면·데이터·API·권한·단계 계획. `docs/design/` 에 판으로 |
| 결정 | `/decide [번호·문장]` | 뭘 결정하라는 거야 · 남은 결정이 뭐야 · D-1 이 뭔데 | 기다리는 결정을 찾아 무엇을 · 왜 사용자가 · 고르면 달라지는 것 · 안 정하면을 번호 없이 풀고 권고 하나. 착수하지 않는다 |
| 팀 | `/team [plan\|setup\|run\|status\|clean]` | 프로젝트 분석해서 에이전트 구성해줘 · 워커에 맡겨 | 분석 → 워커 명단 설계 → 구성 → 위임 · 조회한 상태만 보고 |

**하나만 기억한다면** — 작업을 시작할 때 `/go`, 끝까지 맡길 때 `/auto`.

## 이 명령이 호출되면

1. 위 지도를 그대로 보여준다
2. `git status --short` · `git log --oneline -3` · `HANDOFF.md` 유무를 보고
   **지금 부를 명령 하나**를 이유 한 줄과 함께 권한다

| 저장소 상태 | 권할 명령 |
| --- | --- |
| 저장소가 비었거나 게이트·실행 방법을 모른다 | `start` |
| 에이전트 운영 기록이 없다 (`CLAUDE.md` 절·`docs/team.md` 둘 다 없음) | `start` — 또는 `go` 가 처음에 한 번 묻는다 |
| `HANDOFF.md` 가 있거나 작업 중인 브랜치다 | `go` |
| 미커밋 변경이 있고 확인 기록이 없다 | `check` |
| 확인을 마친 미커밋 변경이 있다 | `ship` |
| 실패·버그 이야기 중이다 | `fix` |
| 상태만 알고 싶다 · 문서와 실제가 맞는지 모르겠다 | `scan` |
| 로컬에서 띄워 보고 싶다 · 서버가 꺼졌다 | `up` |
| 기획서·요구 자료는 있는데 설계 문서가 없다 | `spec` |
| 결정해 달라는 질문을 받았는데 무엇을 정하라는 건지 모르겠다 | `decide` |

## 단계 사이의 공통 규칙

모든 단계가 같이 지킨다. 각 스킬 안에 다시 적혀 있다.

- **되묻지 않는다** — 워크트리 안의 일은 하고 나서 보고한다. 바깥(push·운영 DB·외부 전송)만 묻는다
- **돌려 보지 않은 것을 됐다고 적지 않는다** — 확인한 것과 안 한 것을 나눠 적는다
- **없는 식별자를 만들지 않는다** — 근거로 인용할 번호는 저장소에 실제로 있는 것만
- **도구를 지명하지 않는다** — 그 환경에 있는 것을 찾아 쓰고, 없으면 없다고 적는다
