# 띄우고, 살아 있는지 보고, 띄운 것만 내린다

입력: `$ARGUMENTS` (비었으면 띄운다. `status` · `down [서비스]` · `logs [서비스]` · `clean`)

## 왜 이 명령이 있나

2026-10-05 ~ 11-12 사람이 쓴 메시지 중 **약 28건(프로젝트 5개)이 로컬 기동과 정리**였고, 같은 일로
메모리 4건이 남았다 (`docs/analysis/2026-11-12-memory-prompt-review.md` 2.2).

> *"도대체 컨테이너를 몇개를 띄워놓고 지우지도 않고 있는거야."*
> *"frontend 내려갔어. 다시 올려줘."* · *"로컬 백엔드 또 꺼진거 아닌가?"* · *"8888포트는 왜 또 꺼져있지?"*
> *"니가 띄운 shell을 모아 볼 수 있는 방법이 뭐가 있어?"*

실패는 네 모양이다.

1. **세션과 함께 죽는다** — 대화가 끝나거나 명령이 시간 초과되면 띄운 서버도 내려간다
2. **무엇을 띄웠는지 모른다** — 포트·PID·로그가 기록되지 않아 "꺼졌어" 를 들어도 무엇을 다시 올릴지 다시 찾는다
3. **넓게 죽인다** — 이름 패턴으로 프로세스를 죽여 다른 작업 공간·다른 프로젝트의 개발 서버 둘이 같이 죽었다(2026-10-17)
4. **컨테이너가 쌓인다** — 전체 스택·일회용 컨테이너를 띄우고 지우지 않는다

`check` 는 검증 단계다. "띄워 두면 내가 본다" 는 검증이 아니라 실행이고, 띄운 뒤에도 살아 있는지·어디서
로그를 보는지·무엇을 내릴지가 남는다. 그래서 따로 둔다. **이름이 `run` 이 아닌 것은** 그 이름을 내장 스킬이 쓰기 때문이다.

## 세 규칙

1. **띄운 것만 내린다.** 기록에 적힌 PID(와 그 자식)와 이 프로젝트의 컨테이너만 내린다. 이름 패턴으로
   찾아 죽이지 않는다. 포트를 기록 밖 프로세스가 쓰고 있으면 그것은 남의 것이다 — 죽이지 않고 누구인지(작업 디렉터리) 보고한다
2. **응답을 받아 본 뒤에 "띄웠다" 고 한다.** 웹·API 는 주소를 한 번 호출해 상태 코드를, 그 밖은 포트가 듣고 있는지를 본다.
   프로세스가 떴다는 것만으로는 띄운 게 아니다 — 시작 직후 죽는 일이 흔하다
3. **기록은 한 곳이다.** 저장소 루트의 `.tuzi/up/` — `services.tsv` 한 장과 `logs/<서비스>.log`.
   다음 세션·다른 에이전트도 이 파일 하나로 무엇이 떠 있는지 안다

```
# .tuzi/up/services.tsv
서비스	종류	포트	PID|컨테이너	주소	로그	시작
web	host	3100	48211	http://localhost:3100	.tuzi/up/logs/web.log	2026-11-12 13:40
postgres	container	5432	app-postgres-1	-	(컨테이너 로그)	2026-11-12 13:39
```

`.tuzi/` 가 무시 목록에 없으면 `.git/info/exclude` 에 더한다 — 추적 파일(`.gitignore`)은 고치지 않는다.

## 먼저 정해진 방식을 찾는다

띄우는 방법은 프로젝트마다 이미 정해져 있는 경우가 많다. **이 순서로 보고, 앞에서 정해져 있으면 그대로 따른다.**

| 순서 | 무엇 | 예 |
| --- | --- | --- |
| 1 | `CLAUDE.md` 의 `## 실행` · 「하면 안 되는 것」 | "워크트리에서 `run-local.sh` 금지 — 전역 프로세스를 죽인다" |
| 2 | 저장소의 기동 스크립트 · 작업 공간용 포트 배정표 | `scripts/orca/run.sh` + `worktrees.tsv` |
| 3 | 패키지 매니페스트의 `dev` 스크립트, compose 파일의 서비스 목록 | |
| 4 | 기본값 — 아래 | |

**기본값: 앱은 호스트 프로세스, 미들웨어만 서비스당 컨테이너 하나.** DB·캐시·저장소(postgres·redis·minio 같은 것)만
compose 에서 **그 서비스 이름을 골라** 올리고, 웹·API·워커는 호스트에서 개발 모드로 띄운다. 앱이 컨테이너 호스트명을
보고 있으면 실행 환경 변수로 `localhost:<포트>` 를 덮는다. 일회용 작업(버킷 생성·마이그레이션 도구)은 끝나면 지워지는
방식으로 돌린다. compose 전체 스택을 올리지 않는다 — 사용자가 불어난 컨테이너를 모두 지우고 정한 기준이다.

## 절차 — 띄운다 (인자 없음)

1. **기록을 읽는다.** 기록된 서비스 중 이미 살아 있고 응답하는 것은 다시 띄우지 않는다.
   `다시 올려줘`·`꺼졌어` 는 **기록 중 죽은 것만** 다시 올리라는 뜻이다. 죽은 이유를 로그 끝에서 한 줄 찾아 보고에 적는다
2. **포트를 본다.** 띄울 포트를 기록 밖 프로세스가 쓰고 있으면 규칙 1. 프로젝트가 포트를 고정해(OAuth 리다이렉트 등)
   한 번에 한 작업 공간만 뜰 수 있으면, 어느 작업 공간이 쥐고 있는지 보고하고 그 서비스는 띄우지 않는다
3. **세션과 떨어뜨려 띄운다.** 대화가 끝나도 살아 있게 분리해서 실행하고, 표준 출력·오류를 `logs/<서비스>.log` 로 보낸다.
   PID 를 바로 기록한다. 명령의 시간 제한에 묶인 전경 실행으로 띄우지 않는다
4. **응답을 본다** (규칙 2). 시작에 시간이 걸리면 짧은 간격으로 몇 번 다시 본다. 끝내 안 뜨면 로그 끝 20줄을 보고에 붙이고,
   그 서비스는 `안 뜸` 으로 기록한다 — 뜬 척하지 않는다
5. **보고한다** — 아래 형식. 주소는 눌러서 열 수 있게 전체 URL 로

## `status` — 뭐 떠 있어

기록의 각 줄에 대해 PID 가 살아 있나, 포트가 듣나, 주소가 응답하나를 잰다. 기록 밖이지만 **이 프로젝트 이름이 붙은
컨테이너**가 떠 있으면 함께 보인다(지우지 않는다). 상태만 보고하고 아무것도 띄우거나 내리지 않는다.

## `logs [서비스]` — 로그 어디서 봐

로그 파일의 경로와 끝 30줄을 보인다. 사용자가 직접 따라 볼 명령 한 줄을 함께 준다(`tail -f .tuzi/up/logs/web.log`).
컨테이너는 그 컨테이너의 로그 명령을 준다. 모든 로그가 `.tuzi/up/logs/` 한 곳에 있다는 것이 "띄운 셸을 모아 보는 방법" 의 답이다.

## `down [서비스]` — 내려줘

1. 기록에서 대상을 고른다. 서비스를 안 적었으면 기록 전체
2. PID 가 아직 그 포트를 쥐고 있는지 다시 본다 — PID 는 재사용된다. 다른 프로세스가 됐으면 내리지 않고 기록에서만 지운다
3. 그 PID 와 자식만 끝낸다. 컨테이너는 기록한 것만 멈춘다. **볼륨은 지우지 않는다** — DB 데이터다
4. 포트가 비었는지 확인하고 기록에서 지운다

## `clean` — 컨테이너 정리해줘

이 프로젝트의 컨테이너(compose 프로젝트 이름·저장소 이름이 붙은 것)를 **먼저 목록으로 출력해 센 뒤** 멈추고 지운다.
기록에 있는 미들웨어도 포함한다. 다른 프로젝트의 컨테이너는 목록에 "다른 프로젝트 — 손대지 않음" 으로만 보인다.
볼륨·이미지는 사용자가 그 말을 했을 때만 지운다. 머신 전역 정리(`docker system prune` 같은 것)는 하지 않는다 — 다른
프로젝트의 데이터까지 지운다.

## `check` 와의 관계

`check` 가 실물을 띄워야 하면 이 절차로 띄우고, 검증이 끝나도 **내리지 않는다** — 사용자가 이어서 본다.
검증용으로만 잠깐 띄운 것(E2E 용 컨테이너 등)은 `check` 가 끝날 때 내린다. 어느 쪽이든 기록에 남는다.

## 보고

```
결론: 띄움 (3개 중 3개 응답)

| 서비스 | 주소 | 상태 | PID·컨테이너 | 로그 |
| --- | --- | --- | --- | --- |
| web | http://localhost:3100 | 200 | 48211 | .tuzi/up/logs/web.log |
| api | http://localhost:8000/health | 200 | 48230 | .tuzi/up/logs/api.log |
| postgres | localhost:5432 | 포트 응답 | app-postgres-1 | docker logs app-postgres-1 |

- 다시 띄우지 않은 것: worker (이미 응답 중, PID 47110)
- 띄우지 못한 것: 없음
- 내리려면: `/up down` (이것들만 내림)
```

첫 줄은 [묻는 형식](../go/references/asking.md#결과를-보고할-때)대로 결론이다 — `띄움` · `안 뜸` · `일부 (3개 중 2개)`.

## 하면 안 되는 것

- 이름 패턴으로 프로세스를 찾아 죽이는 것 — 다른 작업 공간의 개발 서버가 같이 죽는다
- 포트를 쥔 기록 밖 프로세스를 "충돌" 이라며 죽이는 것
- 전경 실행으로 띄워 세션·시간 제한과 함께 죽게 두는 것
- 응답을 보지 않고 "띄웠습니다" 라고 하는 것
- compose 전체 스택을 올리거나, 일회용 컨테이너를 남기는 것 (프로젝트가 따로 정했으면 그것을 따른다)
- `down`·`clean` 에서 볼륨을 지우는 것, 머신 전역 정리
- 기록 없이 띄우는 것 — 다음에 "꺼졌어" 를 들었을 때 무엇을 올릴지 다시 찾게 된다
