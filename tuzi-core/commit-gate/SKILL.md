# 커밋한다

## 왜 이 스킬이 있나

`커밋` 이 38건이고 `커밋 2 진행해`·`커밋 4 진행해`·`커밋하고 다음 단계 이어가` 처럼
**번호가 붙어 반복**됐다. 커밋은 이 사용자에게 **작업 단위 그 자체**다. 작업이 끝나면
커밋이 따라오는 것이 기본값이고, 묻고 기다릴 일이 아니다.

## 순서

### 1. 게이트를 한 줄로 돌린다

프로젝트가 묶음 스크립트를 제공하면 **그것을 쓴다.** 손으로 고르면 하나를 빠뜨린다.

> 실례 — `typecheck && lint && test` 셋만 돌리고 커밋해 문서 둘이 서식 위반인 채로
> 들어갔다. `lint`(eslint)는 서식 검사기를 보지 않는다. 프로젝트의 묶음 스크립트는
> 넷(`typecheck`·`lint`·`format:check`·`test`)을 `&&` 로 엮어 **첫 실패에서 멈춘다.**

게이트 이름은 저장소마다 다르다. `package.json` 의 `scripts` 에서 가장 포괄적인
하나를 찾아 쓰고, 없으면 있는 것을 다 엮어 돌린다.

### 2. 브랜치를 확인한다

보호 브랜치(`main`·`master`·`develop`·`dev`)에 있으면 **feature 로 분기한 뒤**
커밋한다. 분기 없이 보호 브랜치에 커밋하지 않는다.

### 3. 경로를 명시해 add 한다

**`git add -A` 를 쓰지 않는다.**

> 무슨 일이 일어나나 — 검증 에이전트가 작업 트리의 소스를 고쳤다 되돌리는 방식으로
> 돌 때, 그 사이 `git add -A` 로 커밋하면 **돌연변이 중간 상태가 커밋에 박제된다.**
> 커밋 통계에 파일 하나가 더 뜰 뿐이라 눈에 안 띈다. 에이전트가 나중에 되돌리면
> 작업 트리는 멀쩡해지고 결함은 커밋 히스토리에만 남는다. 실제로 났다.

### 4. 커밋한 뒤 들어간 것을 본다

```bash
git show --stat --oneline HEAD
```

**의도한 파일만 들었는지** 본다. 섞였으면 작업 트리를 건드리지 말고 색인만 되돌려
amend 한다.

```bash
git restore --source=<부모커밋> --staged <경로>
git commit --amend --no-edit
```

`git checkout <커밋> -- <경로>` 는 작업 트리까지 덮어써 다른 작업과 경합한다.

### 5. push·PR·merge 는 사람 확인을 받는다

`master` push 가 곧 운영 배포인 저장소가 있다. 커밋은 로컬까지가 기본이고,
`원격 push 해줘`·`pr 올려줘`·`master에 merge해줘` 처럼 **사용자가 말한 그 턴에만**
한다. "커밋해줘" 에 push 를 끼워 넣지 않는다.

## 커밋 메시지

저장소의 기존 문체를 따른다. 대화형 보고의 존댓말을 커밋 메시지로 옮기지 않는다.

- 제목은 **무엇이 달라졌나**를 한 줄로. 유형 접두(`fix:`)는 저장소 관례가 있을 때만
- 본문은 **왜**와 **어디에 번지나**. 표 하나와 핵심 문단이면 충분하다
- 게이트 결과를 적는다. 다만 길게 붙이지 않는다
- 적은 내용이 파일에 실제로 있는지 `grep` 으로 대조한 뒤 적는다 (`change-report` 스킬 규칙 4)

## "이번만" 과 "앞으로" 를 구분한다

`이번만 push 해줘` 는 1회 허가고, `앞으로는 묻지 말고 push 해` 는 정책 변경이다.
후자면 기록으로 남긴다(메모리·설정). 전자를 정책으로 확장하지 않는다.
