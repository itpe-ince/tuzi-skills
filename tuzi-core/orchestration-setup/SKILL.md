# 오케스트레이션 환경을 구성한다

## 왜 이 스킬이 있나

사람이 쓴 메시지에서 이 축이 **29건(1.8%)** 이다. 건수는 작지만 **대부분이 요청이
아니라 추궁**이다 — 내가 틀린 뒤 사용자가 되묻는 형태로 남았다.

> - *"오케스트레이션 모드를 구성해 달라고 했는데 **구성이 필요 없어서 안한거야?**"*
> - *"가이드 문서에서 **어디까지가 팀 구성 완료 단계고 어디까지가 실행 단계인지
>   모르겠어.**"*
> - *"아 그럼 **현재까지 오케스트레이션 구성은 완료 된거야?**"*
> - *"orca의 오케스트레이션 모드와 서브 에이전트 모드는 **다른건가?** 서브 에이전트로
>   위임하라고 하면 워크트리가 별도로 만들어지는 줄 알았어."*
> - *"그럼 오케스트레이션 모드로 작업할때는 **워크트리 당 git repository가 다른게 더
>   유리한가?** 지금은 하나의 repository인데 이름만 추가해서 워크트리를 만든거잖아."*

같은 지시가 **질문형으로 반복됐다는 것**이 핵심이다. 지시를 못 알아들은 게 아니라
**해 놓고도 무엇이 끝났는지 알려주지 않았거나, 아예 안 했다.**

## 핵심 금지 — 구성 요청을 판단으로 건너뛰지 않는다

> *"구성이 필요 없어서 안한거야?"*

구성해 달라는 요청에 **"이 작업은 혼자 해도 되니 구성이 불필요하다"고 판단해
건너뛰면 안 된다.** 구성 자체가 산출물이다. 사용자는 그 환경을 **이후에 계속 쓸
것**이고, 지금 작업 하나의 효율은 판단 기준이 아니다.

구성이 과하다고 판단되면 **구성을 한 뒤에** 그 판단을 한 줄로 말한다. 순서가 반대면
사용자는 요청이 사라진 것을 나중에 발견한다.

## 절차

### 1. 그 환경의 도구 문서를 먼저 읽는다

오케스트레이션 수단은 환경마다 다르다(워크트리 관리 CLI, 에이전트 디스패치, 터미널
제어 등). **명령을 추측해 쓰지 않는다.** 이 환경에 그런 스킬·CLI 가 있으면 먼저
로드해 읽고, 없으면 없다고 말한다.

### 2. 모드의 차이를 먼저 설명한다

사용자가 직접 물었다 — *"오케스트레이션 모드와 서브 에이전트 모드는 다른건가?"*
구성에 들어가기 전에 이 환경에서의 차이를 **표로** 정리해 보여준다. 최소한 다음이
갈린다.

| 축 | 확인할 것 |
| --- | --- |
| 작업 공간 | 별도 워크트리가 생기는가, 같은 체크아웃에서 도는가 |
| 수명 | 세션이 끝나면 사라지는가, 남아서 다시 붙을 수 있는가 |
| 통신 | 완료 통지·질의 경로가 있는가, 결과만 돌려받는가 |
| 가시성 | 사용자 화면에 진행이 보이는가 |
| 소유권 | 넘기는 것인가(handoff), 감독하는 것인가(coordination) |

**이 표를 추측으로 채우지 않는다.** 도구 문서에서 확인한 것만 적고, 모르는 칸은
"미확인" 으로 둔다.

### 3. 구성 단계와 실행 단계의 경계를 문서에 박는다

> *"어디까지가 팀 구성 완료 단계고 어디까지가 실행 단계인지 모르겠어."*

구성 산출물에는 **반드시 이 경계가 들어간다.**

```
## 구성 단계 (사람이 직접, 또는 1회성)
1. …
2. …
→ 완료 판정: <무엇을 보면 구성이 끝났다고 아는가>

## 실행 단계 (매 작업마다, 코디네이터가)
1. …
→ 완료 판정: …
```

**완료 판정을 각 단계에 붙인다.** 사용자가 *"현재까지 구성은 완료 된거야?"* 를 묻지
않아도 되게 만드는 것이 목표다.

### 4. 사용자가 직접 하려는 부분을 침범하지 않는다

> *"워커는 나중에 구동한다 치더라도 나는 **오케스트레이션 모드를 위한 구성을 내손으로
> 하고 싶은거야.** 그다음에 워커 구동은 너한테 요청하면 되겠지."*
>
> *"난 **환경 구성까지만 직접 하길 원했고**, 실행은 내가 너한테 얘기하면 니가
> 코디네이터니까 니가 알아서 하는거 아니야?"*

이 사용자는 **구성은 자기 손으로, 실행은 위임**을 원한 적이 있다. 구성 요청이 올 때
어느 쪽인지 애매하면 **그 한 가지만 묻는다.**

- "제가 구성까지 해 둘까요, 아니면 UI 에서 직접 하실 절차서를 드릴까요?"
- UI 로 하겠다고 하면 **CLI 절차서와 별개로 UI 절차서를 만든다** (실제로 요청받았다)

### 5. 워크트리 분리를 기본으로 둔다

> *"근데 **워커가 왜 다 여기 코디에이터 하나의 프로젝트에서 다 도는거야?**
> w-backend 는 따로 있는데?"*

여러 영역(프론트·백엔드·테스트 등)을 나눠 돌릴 구성이라면 **영역별로 작업 공간이
분리돼야 한다.** 같은 체크아웃에서 돌면 서로의 변경을 덮어쓴다.

`워크트리 당 저장소를 따로 둘지`는 사용자가 물었던 질문이고 **아직 정해진 답이 없다.**
구성할 때 이 선택을 명시적으로 표에 올려 사용자가 고르게 한다.

| 방식 | 되는 것 | 안 되는 것 |
| --- | --- | --- |
| 한 저장소 + 워크트리 여러 개 | 브랜치가 한 곳에 모여 병합이 쉽다 | 같은 파일을 동시에 고치면 병합 충돌이 쏟아진다 |
| 저장소를 따로 | 완전 격리 | 변경을 모으는 경로를 따로 만들어야 한다 |

### 6. 정리도 구성의 일부다

`worktree 정리해줘` 가 반복됐다. 구성 산출물에 **정리 절차**를 같이 넣는다 — 안 쓰는
작업 공간을 어떻게 걷어내는지. 워크트리 삭제는 워크트리 내부 작업이라 묻지 않고
한다 (`autonomy-scope` 스킬).

## 보고

구성이 끝나면 **무엇이 생겼고 무엇이 아직 아닌지**를 나눠 적는다.

```
## 생긴 것
| 이름 | 경로 | 역할 | 상태 |
| w-backend | …/w-backend | API·잡 | 생성됨, 아직 구동 안 함 |

## 구성 완료 판정
- <이것을 보면 구성이 끝났다>

## 다음은 실행 단계
- <무엇을 말하면 내가 무엇을 하는가>
```

## 하면 안 되는 것

- 구성 요청을 "불필요" 로 판단해 건너뛰는 것 — **이 스킬이 존재하는 이유다**
- 모드의 차이를 추측으로 설명하는 것
- 구성/실행 경계 없는 가이드 문서를 내놓는 것
- 여러 영역을 나눠 돌릴 구성에서 작업 공간을 분리하지 않는 것
- 사용자가 직접 하려는 구성을 대신 해버리는 것
