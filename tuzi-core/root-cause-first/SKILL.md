# 원인을 먼저 적는다

## 왜 이 스킬이 있나

`근본 원인 해결해줘` 가 그대로 4회 반복됐고 `다시 해봐`·`다시 확인해봐` 가 뒤따른다.
**같은 지시가 반복된다는 것은 앞선 수정이 증상만 덮었다는 뜻이다.**

## 핵심 금지

> **증상을 억제하는 코드를 원인보다 먼저 쓰지 않는다.**

다음은 모두 증상 억제다 — 원인을 모른 채 쓰면 결함을 **보이지 않게** 만든다.

- `try/catch` 로 감싸고 로그만 남기기
- `?? 기본값` · `|| []` 로 빈 값을 메우기
- 재시도 횟수를 늘리기
- 타임아웃을 늘리기
- 실패하는 테스트의 기대값을 결과에 맞추기
- 조건 하나를 추가해 그 입력만 피해 가기

이것들이 **정답일 때도 있다.** 다만 원인을 적은 **뒤**에 고른 선택이어야 한다.

## 절차

### 1. 원인을 한 문장으로 적는다

`X 가 Y 를 하지 않아서 Z 가 된다` 형태로 쓴다. 쓸 수 없으면 아직 모르는 것이다.

- 못 쓰겠으면 더 본다. 추측으로 채우지 않는다
- 두 개 이상 쓰이면 둘 다 적고 어느 쪽인지 **가른다** (로그·쿼리·최소 재현)

### 2. 재현한다

재현하지 못한 원인은 원인이 아니라 가설이다. 재현 경로를 보고에 적는다.
재현이 불가능하면 **불가능하다고 적고** 무엇을 근거로 판단했는지 밝힌다.

### 3. 같은 구멍의 다른 입구를 센다

> 무슨 일이 일어나나 — 한 입구를 막고 끝낸다. 몇 주 뒤 같은 결함이 다른 경로로
> 돌아온다. 한 저장소에서 같은 구멍의 **세 번째 입구**를 찾은 기록이 있다.

원인을 적었으면 `grep` 으로 **같은 패턴을 쓰는 다른 호출부**를 센다. 셋을 다 고칠지,
하나만 고치고 나머지를 기록할지는 선택이지만 **센 것을 보고에 적는다.**

### 4. 강제자가 있는지 본다

규칙을 문서나 변환 함수로만 두면 그것을 거치지 않는 코드가 생긴다. 고친 뒤 묻는다 —
**"이 규칙을 어기면 무엇이 막나?"** 답이 "아무것도" 면 그 규칙은 선언일 뿐이다.

> 실례 — 파생 컬럼 규칙을 변환 함수에 적었지만 실 DB 에 생성 컬럼도 트리거도 CHECK 도
> 없었다. 테스트의 페이크만 그 규칙을 검사했다. 원시 SQL·다른 프로세스는 아무것도
> 막지 않았다. "테스트가 초록이면 제품이 맞다"가 성립하지 않았다.

## 보고

`change-report` 스킬 3열에 **원인 한 문장**을 덧붙인다.

```
**원인** — 세션 검사기가 `exp` 를 읽지 않아 지난 토큰이 통과했다.
**같은 패턴** — `grep` 으로 3곳. 2곳은 이번에 함께 고쳤고, `legacy/` 1곳은 남겼다(사유: …).
**강제자** — 타입으로 막았다 / 막는 것이 없다. 후자면 그렇게 적는다.
```

## 하면 안 되는 것

- "안정성을 위해 try/catch 를 추가했습니다" — 원인을 모른다는 자백이다
- 테스트 기대값을 실제 출력에 맞추는 것. 테스트가 결함을 지적한 것일 수 있다
- 원인 설명 없이 "수정했습니다" 로 끝내는 것
- 재현 없이 "~일 것으로 보입니다" 를 원인으로 올리는 것
